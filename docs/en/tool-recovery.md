# Maintenance capability and unknown inspection recovery

Status: scoped implementation and verification complete. suma1.0.0, T195. Owner: integration agent. [Contract](../../contracts/tool-recovery.md), [PRD](../product/tool-recovery.md), [architecture and AI SOP](../architecture/tool-recovery.md), [interaction design](../design/tool-recovery.md), [verification](../quality/tool-recovery-verification.md).

The authenticated continuous inventory owner declares its maintenance protocol and durable Journal identity. Registration, a one-off report, a tool adapter and a valid credential do not establish this capability. Supported, expired, unsupported and unknown remain distinct. Client deadlines use server checked_at and monotonic elapsed time, including request latency; opening a dialog or replaying an old ACK does not renew freshness.

A current project manager can explicitly authorize reconciliation and release of one exact unknown maintenance reservation for300 seconds. This authorizes no probe, kill, installation, enablement or task execution. The original node reads immutable stop evidence proving returned probes, complete spawn coverage, confirmed native process-tree stops and no pending inventory. A digest or an absent PID cannot replace those facts.

Proof storage alone does not release the reservation. The node first persists the exact receipt and ACK intent; the control plane then closes the original inspection as closed_unknown atomically with reconciliation. Original unknown results and Started history remain. Lost replies recover the same operations, without another probe or kill. A later current periodic snapshot and a separately requested new inspection stay distinct.

An expired but exact last-known protocol and Journal identity may support reconciliation, avoiding a recovery bootstrap deadlock; a new inspection requires fresh support. Current machine credentials, project and Pool authority remain mandatory. Missing durable receipts, unverified trees or changed node identities remain blocked, with explicit isolation and pairing guidance rather than a fabricated stop or deleted Journal.

The original detail panel keeps one primary next action, accurate secondary diagnostic destinations, bilingual states and narrow layouts. Source implementation, protocol fixtures, actual Windows parent/child processes, Worker/Journal recovery, representative UI and production acceptance require separate evidence. The original31 requirements and P0–P7 platform goal remain active.
