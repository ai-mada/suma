# Exact delivery navigation and the original review

Version 1.0.0, stage T-TASK-DELIVERY-NAVIGATION-214. Scoped implementation is present; final App and representative actual verification are recorded in the [quality report](../quality/task-delivery-navigation-verification.md), not assumed here. Owners: workspace and integration. [Contract](../../contracts/task-delivery-navigation.md), [product and AI SOP](../product/task-delivery-navigation.md), [interaction](../design/task-delivery-navigation.md). The original 31 requirements and P0–P7 remain active.

Expand the existing delivery section and follow its formal references. Team plans open the original development/runs team layout with `expert-team:PLAN_ID`. Issues open quality/issues with the exact record. Returned requirements open the requirements view with its exact record. Review opens development/tasks with the exact task record and `task-acceptance:TASK_VERSION:RUN_ID`. Every target retains the current project and uses the shared bounded URL model.

An ordinary current-page click uses the existing navigation guard and SPA callback when supplied. Otherwise the real link works directly. Copying links, keyboard use and opening a new tab remain native operations; a new tab does not leave or invoke the SPA callback in the current page. Loading, errors, refusal and existing locks remove unavailable link targets rather than leaving a disabled-looking URL usable.

**Open review** must open the original Review interface, not merely select the same task. A cross-view locator is generated only for a matching current task version and an exact bound run with current basis. Its consumer matches the current account, organization, project, task, version and run, then invokes the original review opener once. It makes no extra API request, changes no run selection and submits no decision.

Malformed links or changed scope/basis explain how to reopen from current delivery data. Pending original operations take precedence. A refused callback does not consume the intent, but ordinary renders cannot retry it indefinitely; an explicit blocked-to-unblocked transition can permit one more attempt. Consumed intents do not reopen after data refresh or A→B→A changes. A complete new link visit is a new navigation intent.

The shared model, original TaskDeliveryPanel, TaskAcceptanceLocator and thin App callbacks form this change. Existing roles, project authorization, immutable dispatch plans, independent tests, Review and baseline dual-CAS gates remain authoritative. A locator is not `can_accept`, and test counts never grant approval. No backend API, table, generated DTO, dispatcher, candidate/test ownership projection or replacement review form is added. Actual code execution, vendor/model use, full-device coverage and production acceptance are outside this navigation claim.

After a matching locator opens Review, the original route consumes only that account/project/task/panel intent. A parent remount cannot reopen it. The original run selector now keeps its explicit initial selection while options load and preserves later manual choices; pending Review requests retain their original body and operation key.
