# suma documentation

T-P4-011 carries proven native diagnostics through the actual Runner, durable journal, authorized HTTP boundary, DAG events and UI. A single Go catalog now generates the native SDK's 46 entries; these are included in the backend's 778 keys. The frontend has 2,804 keys per language. Version 1 `ToolDiagnostic` contains a key and typed parameters, while original messages and execution/usage facts remain independent. The UI can switch languages and expand the original reason without another execution; disclosure state follows the original event as the rolling list changes. Command, agent and test nodes request one allowlisted Runner command identifier; task/script references retain their separate custom-worker semantics. See the [design and development SOP — Chinese original](../agents/native-diagnostics.md), [verification — Chinese original](../quality/native-diagnostics-verification.md) and [compact summary](../quality/native-diagnostics-summary.json).

The final local checks passed 1,131 Go test events, 544 web tests in 46 files and 47 non-web tests, with type, build and generated-contract checks. An actual isolated native process received one HTTP 429 from a loopback fixture: one failed run, one attempt, ten durable events and five tool facts, with usage explicitly unreported. Language changes and refresh preserved the same raw run and events. Two UI intake actions, with a refresh between them, retained one issue and one draft requirement; the task stayed todo and was not accepted. This verifies the diagnostic path, not a paid vendor model or development acceptance. Other language surfaces, cross-platform installation and the full P0–P7 scope remain in progress.

The historical T-P4-010 stage added controlled DAG diagnostics, structured workflow validation, three runtime command entry points and native SDK/CLI display. Its 731 backend keys and separate 46-entry native catalog describe that earlier cut; Runner propagation was completed in T-P4-011. Original error identities, model/tool payloads and immutable evidence remain independent of display language. See the [historical design — Chinese original](../architecture/runtime-localization.md) and [historical verification — Chinese original](../quality/runtime-localization-verification.md).

Status: implementation in progress. The platform's full accepted scope is tracked in the [implementation ledger](../delivery/implementation-plan.md); a completed local stage does not constitute acceptance of the whole platform.

suma is an intelligent development platform for organizations, teams, projects, requirements, design, execution, testing, human acceptance, releases and issue feedback. Business acceptance, execution state, test evidence and deployment are distinct facts.

The current internationalization work introduces Simplified Chinese (`zh-CN`) and US English (`en-US`) with extensible language catalogs. UI language, business time zone and source content are separate concerns. Original user documents, code, tool output and immutable evidence retain their original language. Unsupported legacy diagnostics are explicitly marked rather than silently replaced by an imprecise translation.

The T-P4-006 baseline verified 671 bilingual frontend keys and 93 backend messages for authentication, common records, shared pools, CLI and desktop foundations. Its two-project fixture completed parallel development, candidate tests, test-account reviews and deduplicated feedback; real vendor models, stakeholder sign-off and production acceptance remain separate. The following stage added persisted account/organization preferences and domain catalogs for workflows, tools, scheduling, team governance and planning. T-P4-008 migrated the remaining 18 owned frontend modules, with 2,798 keys per language and 123 backend messages. It verified structured errors, actual draft preservation and a local Monaco TypeScript edit/save/refresh flow. Its bounded backend inventory recorded 409 unmatched source-message candidates. T-P4-009 then added 447 exact static messages and 10 explicit parameterized keys (580 backend keys total), with strict cause/source binding and a bounded Go AST coverage gate. Actual rejected requests and login errors were verified in both languages; sign-in alternatives gained separate 44px targets. That gate excludes other producers, non-Chinese and raw dynamic diagnostics. See the [historical backend report — Chinese original](../quality/backend-diagnostics-verification.md) for its exact tested scope; the earlier [pool summary](../quality/execution-pool-summary.json) also remains historical evidence. Library menus, other runtime/configuration reasons, notifications, installers, exports and channels still need individual implementation and acceptance.
