# Governed conflict repair tasks

Stage T-P4-032, suma 1.0.0, locally verified within the recorded scope on 2026-10-27. See the [contract](../../contracts/candidate-conflict-repair.md) and [verification report](../quality/candidate-conflict-repair-verification.md). Full P0–P7 work remains active.

The original conflicted composition remains a failed, immutable fact. A repair creates a **new unstarted task and a new CandidateCompositionPlan**, preserving the exact original failed assignment, complete Git conflict evidence, ordered source candidates and whole-basis digest. A path list alone cannot authorize repair.

Open the folded repair section in the original task. Recorded failure and current repair eligibility are displayed separately. Enter a task title, repair instructions and 1–16 acceptance criteria. Priority is optional and defaults to `medium` before receipt hashing. An omitted owner follows the current user only when exactly one active project human resource matches; otherwise it stays unassigned. Explicitly select the workflow, producer and an available native tool whose administrator has opted into `suma.candidate-conflict-repair.v1`.

Duplicate prevention uses the immutable original composition, assignment, result and evidence identity. Current task/run versions remain part of the fresh whole-basis comparison; editing the original task cannot hide an existing repair or create a second one. A current read or recovered link does not authorize stale sources.

**Create repair task and preview** creates the task and its fixed preview atomically. It does not start a run. Open the exact new task link, inspect its original conflict, sources and fixed tool, then separately acknowledge and start. The host governs native resolution and continuation across all 2–16 ordered sources; no source is silently dropped.

An expired ready repair remains readable. **Refresh fixed preview** requires a reason and explicitly rechecks the same task, conflict, sources, tool and route before extending expiry and advancing the plan version. It creates no task or run and does not change its fixed definition. Tool/workflow replacement remains separate future work.

The repair produces its own sealed candidate, independent formal tests and explicit human Review. The failed original plan never becomes accepted. An accepted repair uses the existing governed integration and downstream baseline binding paths through its new composition ID. Downstream binding does not launch a task, and pending expert plans still require explicit revision.

A managed same-run retry requires a known failed, declared-idempotent node with no executed descendants and current source, tool, route and initiating authority. It creates a new attempt/fence while retaining the old failure. Unknown effects must reconcile the original operation first; they never authorize an automatic model restart or replacement task.

The local tool guide offers a native developer configuration template with runtime entry, manifest and administrator check IDs. Conflict repair is off by default. Changing the checkbox edits the displayed local JSON only; the administrator must actually apply the file, probe/import the capability and enable the profile. A template or advertised capability does not prove vendor availability or production acceptance.

The host dispatch marker and typed repair assignment must agree with the agent, exclusive native input and probed opt-in profile. The authenticated native bridge supplies tools and budgets; the marker is not a read-only model-document purpose and cannot grant ordinary or read-only sessions repair authority.

The browser preserves the exact original create request and operation key for uncertain responses. A 409 retains the draft and requires current readback. Authorization loss hides protected facts, and scope changes abort prior reads. System labels are available in Chinese and English; user instructions, code, conflict paths and immutable evidence retain their original text.

Workflow repair provenance is a passive display of typed host evidence. A native `no_change` seal can mean **No additional edits after completed merges**: its baseline is the completed merge prefix, while the candidate can still differ from the administrator anchor. This wording requires complete repair evidence matching the workspace head. Ordinary or invalid repair facts keep the original no-change wording. Neither display claims independent test, acceptance or target integration success.
