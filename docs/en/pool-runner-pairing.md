# Pair an organization-owned Pool machine

Version 1.0.0. Stage T-POOL-RUNNER-PAIRING-208. Owners: integration, control-plane, Runner and Web agents. See the [contract](../../contracts/pool-runner-pairing.md), [architecture](../architecture/pool-runner-pairing.md) and [scoped verification](../quality/pool-runner-pairing-verification.md).

The original Pool nodes tab now offers **Pair execution machine** as its main entry, with manual registration retained separately. The administrator fixes the node name, slot capacity and credential lifetime. A ten-minute request produces a command containing no token. The target machine generates and saves its random credential in the operating-system store, persists the original proposal identity and sends only its fingerprint. The administrator compares the complete fingerprint and explicitly approves the exact version.

Approval atomically registers the original Pool runner and credential hash with the pairing update, operation receipt and event. This does not create a project grant, start a Worker, report inventory, enable tools or dispatch a task. The machine accepts approval only through a current status check. Revocation, credential generation/expiry and Pool state remain authoritative; an old approval cannot restore permission.

Pool and project Runner identities use separate purposes, closed metadata, credential services and routes. They reuse purpose-neutral file locking and atomic persistence only. `--pair-pool-runner` prepares the identity and exits. Explicit Pool startup uses `--pool-identity`, the original `--pool-config` and a required matching `--control`; configuration scope is checked before reading a credential. There is no plaintext or environment-token fallback in identity mode.

Uncertain writes recover the same body/key. A resolved version conflict requires a fresh read and fingerprint confirmation. Corrupt local navigation preferences do not block authorized history or the original pending operation; an explicit reset changes only the public locator. The approved screen emphasizes returning to the exact node, with another request behind a secondary action. Chinese/English, keyboard focus and narrow layouts use the existing design tokens.

Scoped validation includes a real isolated HTTP/SQLite service, the production Pool workspace, one actual Windows credential account and three deliberately lost committed acknowledgements. The original machine was recovered, an original zero-project-scope Pool session succeeded, and the unchanged credential was rejected after revocation. The task-owned credential was removed and its absence confirmed. This is fixture approval and same-host verification, not human production sign-off, physical distributed deployment or vendor/model execution. The complete 31-requirement/P0–P7 goal remains active.
