# Automatic tool checks and registration

Suma 1.0.0 · T-TOOL-ONBOARDING-176. See the [contract](../../contracts/tool-onboarding-scan.md), [architecture and engineering SOP](../architecture/tool-onboarding.md), [interaction design](../design/tool-onboarding.md) and [verification](../quality/tool-onboarding-verification.md).

The desktop tool entry checks the existing fixed directory once and shows installation observations, protocols and next steps. A manual refresh bypasses the completed 60-second cache; concurrent checks for the same caller and project share one process. Every response, including cached observations, is authorized against the actual current session and project. Browser users receive the existing desktop or execution-node guide instead of a misleading scan of the server.

Selecting an entry opens its existing connection flow. Scanning never installs software, logs in, connects a worker, registers or enables a profile, reads a model catalogue, or starts a coding task. The two Codex entries are separate protocols rather than two products. An installed executable is not a healthy connection or dispatch authority.

Advanced registration preserves the caller, project, worker and expiry of an adopted discovery. Expired observations require a fresh read and explicit adoption while keeping the edited name. A failed file import cannot erase the original provenance. Manual paused configuration remains available and is labelled unverified. An uncertain prior registration is reconciled through its original request and operation ID; expiry cannot turn recovery into a new write.

The current shared Go detection directory, Electron lifecycle and platform registration are reused without another dispatcher, database or runtime dependency. Actual CLI observations, controlled component checks and remaining real desktop or cross-platform acceptance are reported separately. The original 31 requirements and P0–P7 platform scope remain active.
