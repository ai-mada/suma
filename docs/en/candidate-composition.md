# Candidate composition and downstream code baselines

Status: T-P4-031, suma 1.0.0, bounded local verification complete on 27 October 2026. The full platform and production acceptance remain in progress.

Use the existing task detail panel to prepare an explicit integration task. Select a fixed workflow version, its producer and an ordered set of 2–16 distinct accepted source candidates. The server resolves current acceptance, independent tests and sealed bytes. Preview creates no run; explicit start freezes the complete inputs and creates one managed DAG run.

A trusted Runner imports the exact authorized bundles into its private attempt and uses Git's native three-way merge. A clean combined commit is a new candidate. The original workflow independently tests that exact result through `candidate_from`; the existing browser Review gate then determines formal task acceptance. Source acceptance, composition success and passing tests are separate facts.

An accepted composition can use the existing governed target integration path, retaining full-diff review, explicit approval, target CAS, fencing and receipts. Separately, an authorized user may explicitly bind the accepted candidate to an unstarted downstream task. Binding changes its task version and invalidates older previews. Pending expert-plan items require an explicit revision; started runs and historical sources are not rewritten. The downstream run gets the combined code but produces its own candidate, test and acceptance facts.

The same protected baseline panel is available in the downstream task detail. It requires an explicit accepted-composition choice and both the current task and binding versions; it never selects the latest result automatically. Existing runs make the binding read-only. URLs restore an exact composition or open the current task baseline without inventing a plan ID. Recorded workspace facts distinguish the administrator bundle anchor from the selected development input.

Conflicts preserve actual paths and source identities without sealing a clean candidate. Unknown execution uses the original run recovery path, with no automatic replacement run. Keep drafts after a version conflict, read current facts and confirm again. An uncertain response restores only the original request and operation key. The panel is folded by default, isolates account/organization/project/task scopes and keeps source code, human content and provenance literal when switching Chinese/English.

Verification is split into focused checks and the bounded actual journey, covering divergent source composition, independent tests of the exact result, formal review, existing target integration and an actual downstream workspace using both changes. Current authority, private/Pool code access, stale baseline, conflict and unknown boundaries require their own focused checks. Real vendor accounts, physical remote hosts, complete database/capacity/device matrices and production acceptance remain separate parts of the full P0–P7 scope.
