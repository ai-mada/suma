# WorkBuddy云任务提交底层与恢复边界

阶段：T-WORKBUDDY-143；产品1.0.0；[合同](../../contracts/workbuddy-cloud-submission.md)。沿原[工具接入矩阵](../integrations/development-tool-matrix.md)推进，当前仅实现内部协议与持久恢复基础，未开放到工具目录、计划派发或公共API。WorkBuddy云保持planned，完整平台目标仍由唯一实施计划管理。

## 模块职责

| 模块 | 拥有的事实与职责 |
| --- | --- |
| internal/workbuddy | 强类型任务创建、单任务读取和分页HTTP；固定提供方协议、响应边界及安全字段投影 |
| internal/runner/workbuddy_journal.go | 原Assignment下持久提交检查点；一次发送资格、固定依据和准确供应方task_id |
| Runner组合helper | 在检查点成功持久后进行一次创建；恢复只核对原记录，返回真实结果或待核对 |
| 现有DAG／Worker／PoolWorker | 保持唯一调度、租约与执行身份；本阶段不增加并行调度系统 |
| 后续正式接入 | 用户授权、凭据托管、当前权限、进度及预算与候选门禁；不由HTTP库自行推定 |

组合helper为`internal/runner/workbuddy_submission.go`的未导出函数submitWorkBuddyTask，尚未接入Execute或能力发现。模块存在不改变工具目录planned状态，也不形成UI／CLI可派发入口。

现有external workflow使用/runs、dispatch_id和/cancel，不能把URL替换成WorkBuddy便当作兼容。独立HTTP模块复用Go标准库与现有仓库技术，不引入新依赖、不复制商业实现。

## 为什么prepared不能自动重试

速码的稳定操作身份只能保证本地重复调用的处理，不能替供应方创造幂等能力。持久prepared发生在发送之前；崩溃后无法分辨“尚未发送”和“远端已创建但回执丢失”。选择保留待核对会牺牲一次可能尚未发送的请求，但能避免自动制造第二个云任务及重复费用。

流程为：固定依据→持久prepared→仅本次准备成功者POST一次→校验响应→持久task_known。重启遇到prepared停止新增外部作用；遇到task_known只读取准确task_id。网络错误、非预期响应以及本地保存失败均不能复位这条链路。任务列表用于明确读取，不作为相似标题的自动匹配恢复工具。

若响应已提供安全task_id但Journal保存失败，helper返回该Task及OutcomeUnknown错误供后续显式核对，不能因结果对象非空忽略错误；磁盘仍为prepared，后续调用不会重POST。错误分类表示调用发生了什么，持久检查点决定是否仍有一次发送资格，两者不能混用。

提交记录必须与原attempt及冻结输入相匹配。新的目标或凭据不覆盖旧记录；既有未知外部作用仍保留待核对。未来若提供方增加原操作查询或幂等合同，需单独评审、固定版本及验证，不把当前恢复语义静默放宽。

## 数据与安全范围

HTTP客户端接收临时调用凭据，正式接入前不自行引入凭据存储。公共任务结果只保留核对所需字段，丢弃供应方返回的ACP凭据和连接／沙箱地址，避免它们经Journal、错误或状态读取扩散。错误不回显Authorization和原始响应正文。

可信提供方与传输由代码／受控测试配置固定，禁止任务输入决定出站地址；不跟随可能转发凭据的跨地址重定向。响应采用明确大小上限、状态码及类型校验；task_id按准确字符串处理，不经浮点数字转换。未知供应方状态保留未知语义，不能升级为速码成功。

这不实现云文件系统隔离。未来产物即使能下载，也须核验来源、字节限制与摘要，并在受控环境导入固定代码候选；候选独立测试和人工验收继续保持原门禁。远端进程停止、供应方账单与硬预算同样需要单独的可信证据。

## 实施与验收层次

当前先验证强类型客户端及持久状态机，用本机服务器覆盖正常和异常协议，不调用厂商账户或模型。真实验收必须另有用户授权、真实供应方task_id、结果、用量与恢复证据。没有ACP、权限交互、候选和取消能力时，不显示“完整接入”“可安全自动重试”或“已停止”。

本阶段不新增用户操作页面；后续接入时必须让用户看见提交状态、最后读取事实与可采取的下一步。prepared应说明结果待核对且无法自动重发，task_known应链接原对象并保留其范围；源数据不可读时不能降级显示成功或清除旧任务身份。
