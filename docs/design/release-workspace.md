# 发布工作区交互设计

日期：2026-10-24。状态：P5 交互合同与首轮界面实现说明；真实部署、故障恢复与浏览器验收由主集成记录单独确认。范围为发布运维的纵向路径，保留既有组织、项目主导航。新浏览器界面独立构建，旧桌面冻结产物不随本轮界面修改而重打。

设计沿用当前紧凑专业工作台、浅深色主题和本地令牌。已读取产品设计工作流与 12ui 规范；遵循已确认的外部上传禁令，未调用远程设计服务或上传材料。以 [发布执行合同](../../contracts/release-execution.md)、[发布控制面合同 v1](../../contracts/release-control.md) 和实际 Go DTO 为映射依据。界面已有只读制品/证明、固定候选、环境配置、计划预览/保存/审阅/执行、部署读取/核对/独立回退准备；有入口不代表实际副作用已被验收。

## 1. 用户任务与现有边界

发布负责人需要回答：“准备交付的究竟是哪一份文件，依据是否仍有效，获准改变哪个环境，真实执行了什么，失败后环境现在是什么？”审阅者需要在一个可分享的计划页看清影响和证据，执行者需要按同一计划操作，故障处理者需要定位原操作并核对真实环境。

P5 之前的依据来自 `apps/web/src/App.tsx`、`api.ts`、`navigation.ts`，以及 `internal/platform/records.go`、`delivery.go`、`http.go`、`internal/runner/external.go`：

- “发布运维”现有“版本发布”“运行能力”两个页签；版本使用通用记录表单，包含版本号、说明、负责人和关联任务 ID。
- `/releases` 当前是登记资料。服务端拒绝直接把登记状态写成 `published` 或 `deployed`；填写下载地址、测试文字或版本号不产生制品和部署证明。
- 任务验收、真实运行、问题回流已有独立路径；工作流测试可固定一个上游干净提交。“代码测试候选”与本设计的“发布候选”是不同对象。
- 现有外部工作流桥接有管理员配置的端点、静态凭证、dispatch 标识、轮询与未知结果；尚不能据此宣称已有部署授权、制品校验、环境代数或发布成功。

目标路径是“收取并校验真实制品 → 固定不可变发布候选 → 选择环境并生成计划 → 审阅并批准精确计划 → 执行环境变更 → 观察健康 → 核对或另立回退计划 → 问题回流”。用户可先登记版本资料，但首轮该通用记录与候选/计划没有发布事实外键，不能靠版本标题相同或填写任务 ID 冒充关联；登记不是部署前提。不采用把所有动作塞进一个可改状态下拉框的交互。

## 2. 事实分层与用户名称

| 用户名称 | 证明的事实 | 页面不得推断的结论 |
| --- | --- | --- |
| 版本资料 | 人工填写的版本号、说明、负责人、范围 | 已收到文件、已构建、已验收、已部署 |
| 制品文件 | 服务端已收到并按摘要校验的真实字节、大小、类型 | 构建来自指定提交，或包测试已通过 |
| 构建证明 | 可信执行产生的源提交、构建过程与输出摘要绑定 | 已完成安装测试、正式验收或环境发布 |
| 包测试证明 | 指定制品摘要在指定平台、测试策略下的真实结果 | 其他平台也已通过、生产健康或已获部署批准 |
| 发布候选 | 固定制品、构建/测试证明与交付范围的不可变集合 | 依据以后永不失效、对所有环境都已获准 |
| 正式验收 | 有权限的人对精确任务/候选依据作出的结论 | 部署环境已变更、部署审批已通过 |
| 部署计划 | 对某个环境和当前代数的一次可审阅变更方案 | 已经执行或获得无限期授权 |
| 部署批准 | 对精确计划及依据的有效批准记录 | 图中普通“审批节点”成功、Runner 凭证即有部署权 |
| 部署记录 | Provider 持久操作与真实目标切换观察 | HTTP 健康、业务验收、故障已修复 |
| 健康观察 | 按固定策略对实际服务地址和内容的观察 | 未覆盖功能均正常、失败时已回退 |
| 回退记录 | 经独立计划和授权执行的另一笔环境变更 | 原部署从未发生、原问题自动关闭 |

界面用“制品指纹”解释规范化内容清单的 SHA-256，清单覆盖各真实文件的路径、长度和文件摘要；单个 blob 的摘要另称“文件指纹”。环境同时保留“最高已预约序号”（`generation`，失败或未生效也不回退）与“当前内容序号”（`active_generation`，实际活跃内容）；下一次写入以前者作 CAS 基准。两者不一致时解释存在未生效或待核对尝试，不能把旧活跃序号当成可用写入代数。完整摘要、run/node/attempt/fence 放入“技术依据”，仍可复制和深链查看。未知显示“尚未确认”，空证明显示“尚无证明”，`0` 与 `null` 分开。

首轮只支持本机 `local_static_site_v1` 和 `static_site_v1` manifest 加真实 blob，不提供浏览器人工上传、ZIP 导入或任意下载地址导入，也不提供 Docker/云端发布。Windows 安装器及其安装/GUI 证明属于后续制品类型；不能因本次桌面包已构建而补造这些证明，或把它投向静态站点 Provider。

## 3. 信息架构与布局

保留主导航“项目概览、需求规划、开发协作、质量验收、发布运维、知识空间、项目设置”，保留组织切换、当前项目入口和项目上下文。只扩展“发布运维”内的页签：

| 页签 | 用户目的 | 主操作 | 详情内容 |
| --- | --- | --- | --- |
| 版本资料 | 整理交付范围、版本说明 | 登记版本；进入发布候选 | 版本资料与登记范围；首轮不推断其与候选/部署的关系 |
| 发布候选 | 固定准备发布的真实内容 | 固定发布候选 | 不可变内容、构建/包测试证明、正式验收依据、当前资格 |
| 制品文件 | 查看 Runner 收取的真实文件、校验与证明 | 进入已配置的真实构建 | 字节回执、摘要、构建证明、包测试 |
| 发布环境 | 了解实际正在提供的内容 | 有权限时配置环境；从候选准备部署 | 当前观察、Provider 状态、策略、占用操作 |
| 部署计划 | 集中处理准备与审阅 | 预览并保存计划 | 不可变计划内容、决策版本、批准与实时阻断原因 |
| 部署记录 | 审阅计划、跟进执行和恢复 | 查看待审计划；核对未知操作 | 精确计划、审批、执行、健康、核对、回退、关联问题 |
| 运行能力 | 查看真实接入和验证状态 | 保留现有入口 | configured/available/verified 各自显示 |

比较过单页向导、资源页签加详情、重建一棵发布专用导航树。采用资源页签：文件入库、审批、部署可能由不同人跨时段完成，独立对象可恢复、可分享；保持既有项目结构。主路径内部使用短步骤提示，允许回到已有对象，不能用“下一步”暗示尚未发生的事实。

桌面列表沿用 `panel`、工具栏、搜索、状态筛选和可加载更多。普通资料详情用侧栏；计划审阅和部署恢复占据内容区全宽，避免在狭窄侧栏中批准长清单。页首只保留项目、版本/环境、事实状态、最后读取时间和当前主操作。中部为证据与差异；右侧窄栏为审批/动作，宽度不足时落到正文之后。事件时间线排在事实摘要之后，不以动画和虚构进度代替真实状态。

复用 `--surface`、`--text`、`--muted`、`--border`、`--accent`、`--green`、`--red`、`--amber` 与现有 `panel`、`Field`、`Empty`、`ErrorNotice`、`Modal`。紫色表示当前动作，绿色只对应已确认通过的具体事实，琥珀色表示等待/未知，红色表示明确失败/失效；每种颜色同时有文字和图标。

## 4. 主路径的交互步骤

### 4.1 登记版本与收取制品

1. “登记版本”填写标题、版本号、说明、负责人和交付范围。保存后显示“仅登记资料”，主操作“选择已有构建制品”，辅助操作“查看构建运行”。关联任务选择真实项目任务，可继续分页；手输 ID 不等于已核验关系。
2. 没有制品时，空态说明“请先运行管理员配置的构建流程，由执行节点上传真实输出”，链接进入当前项目已配置工作流。未配置受信 worker/profile 时显示具体缺项和运行能力入口，不给可点击但不会执行的演示构建。
3. 首轮制品页只读取普通用户有权查看的已封存 `ReleaseArtifact` 和证明，`sealed` 显示“文件已收齐并封存”。Runner 的 `receiving/missing_blobs` 上传会话不能由浏览器跨用 Runner 凭证读取。尚无封存对象时链接真实运行，不造接收百分比；只有以后明确给出普通用户可读的字节观测时才展示实际进度。
4. 上传中断/回执未知由 Runner 按原会话查询 `missing_blobs` 并复用完整 blob，浏览器查看实际运行事实。首轮不支持 blob 内分片 Range，界面不提供“从某字节续传”、代替执行节点上传或换操作号重跑构建。
5. 摘要、路径或限额校验失败保留真实失败原因，下一步查看运行/问题并准备新的构建输出；旧 sealed 制品不可原地替换。下载仅走有权限的制品接口。浏览器人工填入的文件路径、外部地址和 `passed` 字段均不能产生可信制品或证明。

### 4.2 构建、包测试与固定候选

1. 制品详情分别展示“构建证明”“包测试证明”。每条包含证明来源、源提交、真实 run/node/attempt、制品指纹、策略/平台、观察时间和结论；链接进入既有执行详情。
2. 点击“固定发布候选”，填写候选名称，选择已封存制品及精确构建/包测试运行、节点、尝试，以及真实任务范围。服务端核对同一 manifest 指纹、源提交及任务当前正式验收依据。存在缺项时保留本地准备草稿并列出 `blockers`，服务端不创建一个伪装合格的候选。
3. 候选创建后固定所有对象 ID、版本、摘要和依据。按钮变为“查看固定依据”“准备部署计划”。需要更换文件、范围或证明时创建新候选，不在旧候选中修改。
4. “当前依据有效”由服务端核验，不由前端用已加载任务数或字符串相等推算。旧候选保留历史，即使后来任务变更、证据撤销、策略升级；这些变化会影响其后续使用资格。
5. “正式验收依据”展示候选固定的任务版本、依据摘要，以及可读取的真实验收人、结论和理由。首轮候选创建要求任务已在既有任务验收流程正式通过；不新增一个重复的“候选验收通过”开关。部署审批是后续另一项权限和结论。

### 4.3 生成并审阅部署计划

1. 从候选点击“准备部署”，选择环境，显示“当前实际内容”“准备部署的内容”，各有候选/制品指纹和观察时间；环境另列最高已预约序号、当前内容序号及未知屏障。候选属于项目；PlanInput 只绑定候选和环境，不虚构 `release_id` 关系。没有有效观察时显示缺项，不默认环境为空。计划创建阶段仅展示拟使用/拟预约序号，实际预约以 execute 成功回执为准。
2. 环境、目标、健康策略、Provider 配置来自管理员配置。普通用户不能输入任意目标路径、外部工作流、执行命令或审批节点来取得部署权限。
3. 先“预览计划”，读取服务端门禁与当前差异；预览不是审批对象。确认后“保存部署计划”，引用 `candidate_id` 并保存不可变计划 revision/hash。未保存的选择只称“准备信息”；修改任一输入后显式提示“选择已变化，请重新生成计划”，先前批准不能跟随选择迁移。
4. 计划页必须展示：项目与环境；部署/回退类型；当前与目标候选、指纹及代数；交付范围变化；构建和包测试依据；正式验收依据；健康策略；Provider 与目标配置版本；影响与已知限制；允许的恢复/回退方式；全部门禁及审批要求。
5. 每一条范围/证据有名称、当前状态和详情链接。列表标出“已加载 x / 总计 y”；服务端门禁必须覆盖全部范围，不把屏幕上已加载部分当成完整计划。批准入口在完整计划摘要/门禁读取成功后才启用，不要求用户滚动到底制造虚假确认。
6. 审批表单选择“批准本计划”或“退回准备”，理由必填，旁边持续显示精确计划号/revision/hash、候选指纹和环境预期序号。首轮仅当前浏览器项目 admin 或组织 owner/admin 可批准/执行；developer 可准备，普通 reviewer 不因有任务验收权而得到发布批准权。提交前再次读取服务端有效性；执行时仍须服务端原子复核。成功后的文字为“本计划已获批准”，不是“发布成功”。

### 4.4 执行、健康与问题回流

1. 有权限的人点击“执行本计划”。确认面板使用明确动词“将环境 A 从候选 B 切换为候选 C”，列出固定计划、当前代数、依据和后续健康检查；提交包含稳定操作号及版本。批准者和执行者可以不同。
2. 收到部署对象/操作回执后进入详情。显示真实 Provider dispatch/operation 关联、运行尝试、目标切换观察和事件。接受请求、排队、执行中、切换确认分别呈现；无量化进度时不画百分比。
3. 只有 Provider 观察确认目标指纹和环境代数后，显示“内容已切换”。健康区在真正检查前为“尚未检查”；检查失败仍保留“内容已切换”事实，显式显示“当前内容可能仍是新版本”。
4. 健康记录展示策略、观察地址/探针名称、期望内容指纹、实际结果、时间及覆盖范围。Provider 真正重新检查时产生新的观察记录，不抹去上次失败；浏览器“核对”只读取已认证的持久观察，不冒充启动健康检查。不得把 HTTP 200 自动解释为所有业务功能正常。
5. 失败区显示“查看实际环境”“核对原操作”“准备回退计划”，在 `issue_id` 已存在时显示“查看关联问题”。只有服务端已给出或用户确实创建问题后才显示问题链接；失效/结果未知不能直接伪造“已创建故障单”。
6. 问题回流引用候选、计划、部署、环境代数和相关证据，默认不复制秘密或原始未清洗日志。若已有相同失败来源的问题，打开原问题；再次点击不创建重复问题。原部署记录不随问题关闭而改成成功。

静态网页内容不在工作台 origin 内执行，不用 `innerHTML`、脚本执行或带权限的内嵌 iframe 预览上传内容。“打开站点”仅使用服务端固定站点地址，在独立 origin/窗口打开并断开 opener；工作台中的 manifest/文本预览按文本转义。健康结论来自受控真实 HTTP 观察，不来自用户浏览器打开过页面。

## 5. 部署计划的有效性与变更审阅

计划页分别展示固定审阅依据和当前核验结果。候选提供 `accepted_task_basis_sha256`、计划提供 `revision/sha256/content`；审批/执行决策另有递增 `version`。前端不把这三个值混为同一版本，不自行定义审批有效期或复用条件。首轮计划 revision 固定为 1，内容变化创建新 plan；当前 `eligibility=false` 与 `blockers` 可使历史 approved 不能再执行，原审批审计保留。现有 DTO 提供完整固定目标和阻断 code/message，未提供字段级 before/after 差异或完整当前/目标范围比较；首轮不生成虚构差异表。

计划详情和审阅/执行确认框以精确 GET 读取真实环境名与候选名，只使用 ID、项目一致的返回对象；完整技术标识折叠且可复制。名称暂不能读取时显示短 ID、明确缺少名称并提供重读，不能从标题相似或当前组织角色推测名字。审批人尚无可信姓名映射时只显示短账号标识，完整账号与固定摘要留在审阅技术依据中。

| 变化 | 界面反应 | 允许的下一步 |
| --- | --- | --- |
| 选择了另一个候选、制品、范围、环境或回退目标 | 标为新的准备草稿，旧批准不适用 | 保存新计划并重新审批 |
| 所依赖任务/需求依据变化、验收失效 | 列出项目与变更前后版本及失效原因 | 查看任务，修复或重新验收，再生成计划 |
| 构建/包测试证明被撤销、失败或与指纹不符 | 标为“依据失效”，显示具体证明 | 取得新证明并生成新候选/计划 |
| 环境实际代数、活跃内容或 Provider 配置变化 | 显示“环境已变化”，保留原比较 | 读取实际环境，重新生成计划 |
| 部署/健康策略版本或审批政策变化 | 显示“批准依据已变化” | 查看政策差异并重新审批 |
| 审批人被撤权、批准撤销或按已配置策略过期 | 显示准确原因与失效时间 | 由有权限的人重新审批；不能自动换审批人 |
| 标题等纯展示资料变化 | 显示新资料；是否影响门禁以服务端结果为准 | 不由前端一概失效或一概忽略 |

批准区最多显示“有效”“待审”“已退回”“已失效”这一审批维度；执行维度独立。失效后的批准记录仍保留批准人、时间、计划和原理由。红色失效条同时列原因与可执行修复入口，不只提示“版本不匹配”。

`409` 不能用“把 expected_version 换成新值再执行”处理。资料编辑可保留草稿并比较后重存；部署计划变化须重新生成和审阅，不能无感重基批准。审批或执行的结果未知期间，必须先恢复原操作，禁止同时生成一个新操作号绕过未知副作用。

## 6. 状态与动作表

以下是展示语义，不能作为新增通用记录状态直接写入。接入时按发布合同的实体状态和服务端允许动作映射；未知枚举显示原始状态与“当前版本尚不能操作”，默认关闭写操作。

| 资源/事实状态 | 主动作 | 辅助动作 | 禁止误导 |
| --- | --- | --- | --- |
| 版本仅登记 | 选择构建制品 | 编辑资料、查看范围/真实构建 | 不能直接“标记已发布” |
| 尚未形成可读封存制品 | 查看真实构建运行 | 读取允许的实际输出 | 浏览器不接管 Runner 上传、不跨读其会话或补造完成 |
| 制品待校验 | 读取校验回执 | 查看已收字节 | 不创建可部署候选 |
| 制品校验失败 | 查看原运行/失败原因 | 准备新构建 | 不改旧制品摘要 |
| 制品已校验、证明缺失 | 查看缺少的证明 | 进入真实构建/包测试路径 | 不标“包测试通过” |
| 候选固定、依据有效 | 准备部署计划 | 查看完整固定依据 | 不等于已获部署批准/已部署 |
| 计划待审 | 有权限时审阅本计划 | 查看差异、退回 | 不借图审批代替 |
| 计划获准且当前有效 | 有权限时执行本计划 | 查看批准记录 | 点击时仍需服务端复核 |
| 计划失效/被退回 | 查看变化并准备新计划 | 查看历史批准 | 不自动沿用旧批准 |
| 部署已接收/排队/执行中 | 查看执行 | 刷新/核对；以后有明确接口才开放取消 | 取消请求不等于取消成功 |
| 部署结果未知 | 核对原操作 | 读取 Provider 观察、关联问题 | 禁止直接重试部署、宣告未执行或成功 |
| 内容切换确认、健康未检查 | 查看提供方检查进展 | 查看实际内容、核对回执 | 不显示健康通过或虚构独立检查接口 |
| 健康检查失败 | 查看检查与环境 | 准备回退、打开已关联问题 | 不自动标已回退 |
| 部署明确失败、环境已确认 | 查看失败依据 | 准备新计划或回退 | 失败操作不等于环境没变化 |
| 回退执行中/结果未知 | 查看/核对回退操作 | 查看原部署 | 不提前显示已恢复 |
| 回退目标切换确认 | 查看当前实际内容与健康观察 | 读取提供方回执 | 原部署历史不改写 |
| 已有更新部署 | 查看当前环境 | 查看本次历史操作 | 旧操作不得覆盖新代数 |

执行合同中的三个状态轴分别映射，不复用现有通用 `Badge('succeeded')` 文案：

| wire 轴 | 枚举与用户文案 | 展示约束 |
| --- | --- | --- |
| operation.state | `received` 已受理；`authorized` 授权已确认；`staging` 准备内容；`applying` 正在切换；`checking_health` 正在检查健康；`succeeded` 发布与本代健康已确认；`failed` 本次发布失败；`cancelled` 已确认取消；`reconciling` 结果待核对 | succeeded 必须已有 applied 且本代 health passed；不能把所有 2xx 显示为成功 |
| effect.state | `not_started` 尚未开始切换；`applied` 内容切换已确认；`unknown` 切换结果待核对 | failed + applied 仍表示新内容已激活，不抹去副作用 |
| health.state | `not_checked` 尚未检查；`passed` 本代健康检查通过；`failed` 健康检查失败；`unknown` 健康结果未确认 | 展示其绑定 generation、artifact 与观察时间，不套用旧代健康 |
| 发布投影 | `deployed_healthy` 已部署且本代健康通过；`deployed_unhealthy` 已切换但健康异常；`reconciling` 当前部署待核对 | 投影来自服务端，不是普通 release PATCH 可写状态 |

浏览器 `Deployment` 将副作用与健康摊平为 `effect_state/health_state`，原 Provider 结构保留在 `observation/observations`；初始 `state=queued` 显示“已排队，尚无提供方观察”。控制面 `ReleasePlan.state` 的 `pending_approval/approved/rejected/revoked/executing/completed` 分别为“待审阅/已批准/已退回/批准已撤销/执行中/执行已结束”；completed 不能单独显示为部署成功，仍读取 Deployment 三个事实轴。禁止把 Provider 原始终态和当前环境投影压缩成一枚含义不清的“成功”。

## 7. 未知结果、核对与回退

“核对”表示获取真实外部事实；“回退”表示执行另一笔环境变更，使用不同操作。两者不得共用一个“恢复成功”按钮。

- **回执丢失**：提交前冻结原完整非秘密请求、路径、方法、项目、版本和操作标识，按钮为“恢复原操作回执”。未取得对象 ID 时只以同一 key 重放原 HTTP 请求恢复服务端回执；取得 operation_id 后转为精确 GET/核对，不创建新部署。
- **页面刷新**：非秘密原请求保存在当前标签页的 sessionStorage，按组织、账号、项目隔离；同标签页刷新可恢复原信封。存储失败时在发送前停止，记录损坏时关闭新写入并显示错误；不承诺浏览器关闭、会话存储丢失后的自动恢复，也没有按 idempotency_key 单独查询服务端的浏览器接口。Runner/Provider 凭证、密码、邀请和授权票据不进入此存储。
- **权限丢失或暂缓核对**：可明确选择“保留待核对记录，退出本次编辑”，解除当前页离开保护，保留同一信封并禁止并行新写入；这不是取消、失败、未执行或已回退。恢复会话后由用户显式恢复，不能自动提交。普通未提交表单草稿仅在当前编辑中保留，刷新由离开保护提醒，不承诺永久保存。
- **取消**：显示“已请求取消”；只有 Provider 确认终止且给出目标观察后才显示“已取消”。若已切换，保留切换事实；超时/Runner 离线不能被解释为外部部署停止。
- **核对页**：同时列控制面原计划/尝试、Provider 持久 intent/操作状态、目标当前代数/指纹、健康观察和观察时间；缺失信息逐项标缺失。没有完整真实证据时保持未知，人工 reason 不能单独成为部署成功或未发生证明。
- **准备回退**：从当前环境选择一份明确的历史候选。展示当前到目标的差异、历史证明是否仍可用以及无法自动撤销的影响，生成独立计划与审批。不能把 DAG `compensatable` 解释成环境回退权限。
- **回退竞争**：若当前环境已有更新操作，保留回退草稿并展示新旧代数；要求重新生成计划，不把旧回退目标强制写回。回退失败/未知时显示真实状态并回到核对路径。

Provider 票据或静态凭证不进入普通表单、URL、浏览器持久存储、复制内容或事件输出。用户只看已脱敏的授权记录号和依据。Provider 必须独立核验控制面票据绑定和当前 attempt/fence/环境代数；“按钮已点过”“图中审批成功”不构成权限。

## 8. 深链与项目上下文

延续现有 `URLSearchParams` 路由、浏览器前进后退和 `project/view/sub/record/q/status/layout`。P5 只扩展资源选择，不替换固定导航；以下链接是待实现的路由约定：

| 目的 | 深链示例 |
| --- | --- |
| 版本资料 | `?project=p&view=operations&sub=releases&record=r` |
| 固定发布候选 | `?project=p&view=operations&sub=release-candidates&record=c&panel=basis` |
| 制品校验/证明 | `?project=p&view=operations&sub=artifacts&record=a&panel=proofs` |
| 环境与当前观察 | `?project=p&view=operations&sub=environments&record=e&panel=current` |
| 审阅尚未执行的计划 | `?project=p&view=operations&sub=release-plans&record=pl&panel=review` |
| 部署与核对 | `?project=p&view=operations&sub=deployments&record=d&panel=reconcile` |
| 真实运行依据 | `?project=p&view=development&sub=runs&run=run-id&node=node-id` |

只需新增 `panel` 字段定位依据/审阅/核对段落，计划也复用 `record`，表示当前页签的主对象。不要把部署 ID 放进现有 `run`，否则现有 App 会进入工作流详情。关联环境和候选在计划/部署对象中按 ID 读取，不靠 URL 提供授权。

分享只复制当前可读资源链接，不带 ticket、上传会话秘密、下载凭证或原始输入。刷新精确读对象详情，不要求该对象已在第一页列表中。组织/项目切换先处理草稿和未知提交，再清除跨项目对象引用；切换组织仍沿用已有各组织项目上下文。返回执行证据后可用浏览器返回回到原计划，不丢审批理由草稿。

## 9. 权限、读取和写入反馈

权限由服务端对真实组织/项目身份及环境策略判断；前端不从团队归属或 Runner 配置猜测部署权。首轮 developer 可以提出计划，只有当前浏览器项目 admin 或组织 owner/admin 可批准、执行、撤销及回退；普通 reviewer 只有已有任务验收等明确授予的权限，API/Agent/Runner token 不因此取得发布批准权。读取详情应返回允许动作及禁用原因，例如固定候选、审阅计划、执行、健康检查、取消、核对、准备回退、环境配置；具体 wire 名称由合同确定。制品及证明在浏览器只读，受信执行凭证不出现在普通用户表单。权限变更后刷新当前会话和动作。

| 场景 | 页面反馈与行为 |
| --- | --- |
| 初次加载 | 对应面板显示读取状态，操作区禁用；不展示零部署或全健康占位统计 |
| 真正空列表 | 清楚区分尚无版本、尚未收到文件、无可用候选、无环境配置、无部署；根据实际权限提供下一步 |
| 筛选无匹配 | 说明是已加载范围/服务端范围，保留筛选和加载更多；不误称项目没有内容 |
| 读取断线 | 保留最后读取的记录并显示时间；“当前环境”改为“上次观察”；不可据旧快照批准或执行 |
| Provider 离线 | 配置状态与连接状态分开；保留持久操作和未知结果，不生成空的成功记录 |
| 401 | 保留非秘密草稿/恢复引用，要求恢复会话；不在新登录后自动提交部署 |
| 403 | 显示缺少的动作权限和有权角色说明；可读依据保留，服务端不允许读取的内容不泄漏 |
| 404/跨项目对象 | 显示对象不存在或不可访问；不自动切换项目寻找它，不回退到列表首项 |
| 版本冲突 | 保留表单和原依据，读取当前对象与结构化差异；新计划必须重新审阅 |
| 提交超时/5xx/成功回执损坏 | 结果未知，保留原信封；只能恢复原操作，不解锁可变字段后重发 |
| 部分分页读取失败 | 保留已加载数据及覆盖范围，重试当前游标；不删除旧数据、不据缺页批准范围完整 |
| 依据读取失败 | 展示缺失的具体依据，批准/执行不可用；不能降级为忽略门禁 |

普通资料编辑复用稳定操作号、版本、原生表单实际值和已有离开保护。服务器已接收并返回部署 ID 后，长任务可继续后台执行，用户可以导航；尚未确认提交结果或存在未保存草稿时按既有离开保护处理，或显式保留待核对记录后退出编辑。任何恢复都不跨项目复用操作号。

## 10. 窄屏与键盘方案

- **宽屏**：沿用项目侧栏和顶部上下文；计划页主体/动作栏分列，证据表可独立横向滚动。1920 宽度仍按当前内容最大宽度组织，避免整屏稀疏卡片。
- **中屏**：768 宽度下计划摘要、差异、证明、审批顺序堆叠，顶栏保留当前项目和返回入口；页签横向滚动，选中项可见。动作区不能覆盖内容或错误提示。
- **窄屏**：390 宽度下详情改为内容区全宽并保留返回按钮；计划比较改为逐字段“当前/将变更为”，摘要可展开完整复制。列表改为带字段标题的紧凑卡片，主要动作可见；只有证据/事件明细局部滚动，不让整页产生横向滚动。
- **表单与触控**：移动端主要按钮和图标触控区域至少 44px，标签不缩成无名称图标。长摘要、URL、错误文字换行；不会用截断内容作为唯一审批依据。
- **键盘**：按钮、复选框、选择器都可用键盘；不要求拖放才能选择候选/制品。页签沿用左右方向键、Home/End；表格行标题为实际按钮/链接，不要求点击整行。
- **审阅比较**：折叠区用带 `aria-expanded` 的按钮；变化有文字标签，不能只靠红绿。每段有标题和跳转锚点；完整摘要支持复制，复制结果用 polite 状态说明。
- **对话框**：沿用 Radix 焦点约束；打开后先读标题/说明，Escape 只关闭可安全离开的准备/确认框。关闭后焦点回到原触发元素，触发元素已卸载/禁用时回到 `#main`。存在未知提交时解释离开保护，提供恢复原回执或显式保留待核对记录后退出编辑。
- **动态状态**：状态改变用 `aria-live=polite`，明确失败用 alert；事件列表不抢走焦点，不每轮轮询重复朗读全部输出。长任务不因后台刷新重置滚动和审阅输入。

## 11. 实现映射与合同接入要求

后续实现使用独立的发布 DTO 和专门状态映射，不把新实体全部塞进通用 `RecordItem.data` 或通用 `statusNames`；同一 `succeeded` 在“构建”“部署”“健康”中含义不同。下表给出可直接拆分的页面数据边界，字段是所需语义，配套合同定稿后逐项映射实际 wire。

| 页面模型/建议组件 | 读取数据 | 写入/动作 | 必须保留的来源与边界 |
| --- | --- | --- | --- |
| `ReleaseList` / `ReleaseDetails` | 既有版本资料及登记范围 | 版本资料 CRUD；打开候选页 | 旧 `/releases` 的 `version`、`data.release_version`、`data.task_ids` 仅登记资料，首轮无候选外键 |
| `ArtifactReceipt` / `ArtifactDetails` | 普通用户可读的封存制品、manifest、proofs | 浏览器只读；链接真实构建 | 不跨读 Runner 专用上传会话；sealed 不等于构建成功 |
| `ArtifactProofs` | 构建/包测试证明、可信命令、平台、源提交、attempt/fence | 打开真实运行；按策略请求验证 | 证明必须绑定精确 artifact digest，人工备注另列 |
| `ReleaseCandidateDetails` | `/release-candidates` 固定 artifact/proofs/task basis、当前资格及 blockers | 固定新候选、打开既有任务验收、准备计划 | 不可变与当前资格是两个维度；无直接改状态/编辑接口 |
| `EnvironmentDetails` | 配置版本、实际 active generation/digest、观察时间、策略、历史 | 有权配置；请求当前观察/健康 | desired 与 observed 分开；不向普通用户返回可写本机路径/凭证 |
| `DeploymentPlanReview` | plan `revision/sha256/content`、候选basis、当前 eligibility/blockers/allowed_actions | preview→create→approve/reject/revoke→execute | expected_version 是决策版本；revision/hash 是固定内容；不直接改状态 |
| `DeploymentDetails` | 持久 operation/dispatch、运行绑定、Provider 回执、当前环境观察 | 恢复回执、请求取消、健康、问题回流 | 控制面接受、Provider 执行、切换确认、健康独立显示 |
| `DeploymentReconciliation` | 原操作、Provider intent、target generation/digest、证据缺项 | `POST /deployments/{id}/reconcile` 请求读取已认证观测 | 无 outcome/成功/健康自填字段；不能提交人工结论 |
| `RollbackPlan` | 当前观察、明确历史候选、原部署关联、差异 | 创建独立回退计划→审批→执行 | 新操作号、新环境预期代数；原记录不可改写 |

详情读取应按精确 ID。候选/制品等按其实际响应支持 `items/total/next_cursor`；发布控制面 v1 的环境、计划、部署是完整项目 `items/total` 列表，不虚构游标或加载更多。若未来分页，计划门禁仍必须依据全范围服务端核验；部分窗口不能补算项目统计。交互层按组织/项目/资源 ID 取消旧读取并丢弃过期响应；后台读取不得覆盖本地审阅草稿或更换未知写入的原信封。

### 11.1 独立发布候选的实际映射

独立持久资源采用以下实际 Go DTO 与 HTTP 路由，真实流程验收另行记录：

- `POST /release-candidates`：`project_id,name,artifact_id,build_attestation_id,package_test_attestation_id,tasks:[{id,expected_version}],idempotency_key`。成功返回候选详情 envelope。
- `GET /release-candidates?project_id=...&limit=...&cursor=...`：`items:[候选详情envelope],total,next_cursor`；`GET /release-candidates/{id}?project_id=...`：`{candidate,eligibility:boolean,blockers:[{code,message}]}`。
- 固定对象包含 `id,project_id,name,artifact_id,artifact_sha256,source_commit,build_attestation_id,package_test_attestation_id,accepted_task_basis_sha256,build_proof,package_test_proof,tasks,created_at`。任务依据是 `{id,version,run_id,review_id,sha256}`；proof 的执行身份在 `assignment:{run_id,node_id,attempt,fence,worker_id}`，还包含 kind/artifact_id/manifest_sha256/source_commit/profile_id/profile_sha256/workspace_sha256/created_at。
- 创建时服务端核对 sealed 真实字节、由成功最终 Complete 派生的证明、同一 digest/source commit、每个任务的当前正式 accepted 依据；客户端不提交 `passed` 或自报 basis 摘要。
- 候选没有编辑/替换接口。详情的当前 eligibility/blockers 是新核验结果，不更改原冻结对象。部署计划引用 `candidate_id`，避免用户在计划里重新拼装另一组制品/证明。

候选表单从所选 `artifact.proofs` 分别选择 kind=build 与 kind=package_test 的真实 proof，显示配置名、运行/节点/尝试，只提交所选证明 ID。不从最近一条成功运行推断默认可用，不让高级 JSON 填写“通过”。提交 `tasks` 是带版本的对象数组，与旧版本资料中的字符串 ID 数组分开处理。服务端根据当前持久记录核验 fence、受信 profile 和实际证明，浏览器不自造这些字段。

### 11.2 环境和部署控制面的精确映射

以发布控制面 v1 的 `/environments`、`/release-plans`、`/deployments` 命名为准，不创建另一套 `/release-environments`、`/release-operations` 或早期 `/releases/{id}/plans` 浏览器适配。

| 用户动作 | API 与提交字段 | 读取后呈现 |
| --- | --- | --- |
| 读取可配置提供方 | `GET /release-providers?project_id=...` | `items:[{id,site_ids,kind,capability_state}],total`；只使用管理员真实登记的非秘密选项，configured 不等于已验证 |
| 读取精确环境 | `GET /environments/{id}?project_id=...` | Environment；刷新深链无需先遍历列表 |
| 新建环境 | `POST /environments`：project_id/name/provider_id/site_id/health/idempotency_key | Environment；仅说明配置已保存，不把它标成连接/部署验证通过 |
| 编辑/归档环境 | `PATCH /environments/{id}`：project_id/expected_version/idempotency_key/name?/status?/health? | status active/archived；不能换绑 provider/site，活动屏障时策略/归档被拒 |
| 计划预览 | `POST /release-plans/preview`：PlanInput | preview_sha256、environment、candidate_id、action、health、eligibility、blockers、allowed_actions；保留当前完整准备输入 |
| 保存计划 | `POST /release-plans`：相同 PlanInput + preview_sha256/idempotency_key | 不可变 content/revision/sha256；输入变更立即丢弃旧预览，必须重算 |
| 批准/退回/撤销 | `POST /release-plans/{id}/approve`：project_id/expected_version/idempotency_key/plan_revision/plan_sha256/decision/reason | decision approved/rejected/revoked；保留 actor、理由与固定摘要 |
| 执行本计划 | `POST /release-plans/{id}/execute`：project_id/expected_version/idempotency_key/plan_revision/plan_sha256 | Deployment.operation_id；进入精确详情，仅受理不能显示已部署 |
| 读取原部署 | `GET /deployments/{operation_id}?project_id=...` | 真实 observation/observations、effect_state、health_state、issue_id、allowed_actions/blockers |
| 核对原操作 | `POST /deployments/{operation_id}/reconcile`：project_id/expected_version/idempotency_key | 仅请求读取并保存已认证 Provider 观察，不能传 outcome/健康/成功结论 |
| 准备回退 | `POST /deployments/{operation_id}/rollback-preview`：project_id/expected_environment_generation | 可用历史目标和 rollback PlanInput；随后仍走 preview/create/approve/execute，不直接回退 |

`PlanInput={project_id,candidate_id,environment_id,action,expected_environment_generation,rollback_source_operation_id?}`。`eligibility` 在本控制面为布尔，`blockers` 为 `{code,message}[]`，`allowed_actions` 只列当前身份/状态允许的动作；不能误用 execution 草案另一种嵌套 eligibility。表单保留服务端错误码和可展示 message，按 code 做恢复选择。

环境表单从 `/release-providers` 选择提供方及其真实 site_ids；没有可选项时显示“尚未登记本机发布提供方”，指向管理员接入说明，不造演示选项，也不让普通用户手填 URL/根目录/秘密。名称可编辑，既有 provider/site 不可换绑；health 编辑只含已约束的站点内 path、expected_status、expected_file、timeout_ms、attempts，内容摘要在计划生成时由真实 manifest 补齐。

首轮没有独立浏览器 health-trigger/cancel 接口：健康由受控 Provider 流程真实执行，界面只读；取消只在以后明确路由且服务端给出动作时开放。当前未知操作只提供“重新读取”“核对原操作”，不显示无接口支撑的按钮。`issue_id` 有值才给现有问题详情链接，缺少独立回流接口时不承诺点击自动生成问题。

页面建议按独立懒加载模块接入：发布路由只加载发布列表/详情，工作流证据链接才加载现有 Workflow；模型与 API 适配独立，避免候选只读页导入整个工作流编辑器或 IDE。请求按项目/资源隔离，精确详情可以直接刷新恢复；不以增加依赖或重建旧冻结包完成本设计。

### 11.3 已对齐的合同与仍有的限制

1. 已对齐候选 proof-ID 创建请求、不可变任务依据、独立 eligibility envelope 与实际 Go 导出类型；未知新状态保留原值并说明尚未识别。不新增候选人工通过入口。
2. 制品/候选列表支持 20 默认、100 最大游标；环境、计划、部署、发布执行节点与提供方选项首轮返回完整项目列表，不添加伪分页参数。浏览器没有上传会话/missing_blobs 界面，分片 Range、更多制品类型仍待后续。
3. 构建和包测试证明由当前成功 Complete 原子派生；候选任务必须由证明所在同一运行交付且当前正式验收有效。执行节点和命令登记只证明配置，不证明实际构建成功。部署提供方仅支持本机静态站点。
4. 计划预览、精确审批、执行、回退预览已按同一 DTO 映射；完整字段级差异、范围变化统计及独立 coverage 响应仍未提供。不能以摘要不同推算变化任务数。
5. 动作采用服务端 allowed_actions：环境 create/edit/archive；预览 create；计划 approve/reject/execute/revoke；部署 reconcile/rollback_preview。浏览器不从组织角色代推项目管理员权限。首轮没有独立 cancel、health-trigger 或凭证登记大表单。
6. 环境最高预约代数、活跃代数及屏障分开；未知操作保持屏障。原请求恢复使用同 key 重放，尚无单独按 key 查询浏览器 API。跨浏览器/存储丢失的定位恢复仍须服务端审计与管理员介入。
7. effect 与 health 及真实观察历史分开展示；受控核对从已认证 Provider 观察恢复托管执行，原未知事件留审计，不允许浏览器提交 outcome。核对失败保持未知，不能暗示取消/回退成功。
8. 回退必须从真实历史操作取得 input/preview，再另建计划、批准、执行；候选当前依据失效仍可能阻断回退。问题只链接真实 issue_id；没有独立浏览器手工创建发布故障结论的入口。

这些限制不可由前端默认值补齐。缺少服务端能力或依据时显示具体原因并关闭相关写操作；保留已有登记、查看与真实运行链接。接口生成器反射导出响应模型，并为 map 请求/回执维护审阅过的字段 DTO；生成校验不是全部 HTTP 分支、跨字段权限、回执及副作用协议的自动证明。

### 11.4 构建与包测试来源编辑

工作流属性为 test、command、agent 提供候选来源选择，保存 `config.candidate_from`，只列当前连线和 depends_on 确认的静态 command/agent 祖先；清空删除该属性。command/agent 固定候选仅供管理员已配置 ArtifactOutput 的不可变构建，本地 Runner 仍校验实际命令配置和 repository，任意代码命令不会因选择此字段获得构建权限。

test 另有“包测试制品来源”，保存 `config.artifact_from`。从当前项目 `/release-workers` 的 active、未过期、kind=build 命令登记筛选静态构建祖先，并匹配节点唯一命令 alias。登记读取失败有明确重读入口，不把任意祖先标为已配置；实际服务端还须验证当前成功构建尝试、真实制品、fence 和源提交。高级 JSON 保留；无效旧来源可见并可清除。两种来源同时配置必须固定到同一源提交；多分支不会自动合并，实际包测试必须使用管理员 ArtifactInput 命令。

## 12. 后续验收场景

本轮实际验证见[统一报告](../quality/verification.md)与[机器旅程](../quality/evidence/release-browser-execution.json)。已新增需求/问题的“来源与证据”区，使用正式记录中的项目、问题、operation和run标识下钻，不猜测对象名称或伪造已解决状态。弹层Escape由Radix局部消费，保留底层详情与原按钮焦点，避免全局快捷键连带清空record。以下清单继续作为完整范围，未实跑条目不视为已验收。

下列场景是实际验收清单；本页不以界面构建或模型测试代替其执行记录。至少逐项记录：

1. 仅登记版本与下载地址，页面仍明确没有已收字节/构建证明/部署。
2. Runner 上传真实 manifest/blob，浏览器刷新读取同一摘要；传输回执丢失恢复同一对象，不能重复固定不同字节为同一候选。
3. 一个源提交通过测试但产物摘要不匹配，禁止用该证明固定候选/批准发布；Windows 包尚不属首轮类型，不因已有构建产物就显示安装/GUI 验收。
4. 审阅固定候选和全范围计划，依据在批准后变化；执行被拒并展示具体差异，审批理由草稿保留，旧批准没有自动迁移。
5. 普通开发者在可发布的任意 `external_workflow` 中伪造审批/票据输入，Provider 拒绝部署；有效图审批也不能越过环境授权。
6. POST 部署回执丢失、Runner 断线、Provider 重启后按原 dispatch 恢复；没有成功/未执行证据时始终保持未知。
7. 内容切换成功但健康检查失败，显示两项事实；未点击并完成独立回退时绝不标记已回退。
8. 回退请求与另一部署竞争，旧代数被拒；迟到的原部署、取消或补偿不能覆盖更新环境。
9. 同一失败重复点击回流打开同一问题；问题关闭不改变原部署结论。
10. 刷新/深链/浏览器返回、组织项目切换、401/403/404/409、分页断线均保留准确上下文；390/768/1366/1920 与纯键盘可完成同一准备、审阅和恢复路径。

交付设计评审时核对“用户看到的每个事实是否有明确的服务端来源、每个动作是否有权限/版本/恢复协议”；实现与真实验收由后续阶段单独记录。
