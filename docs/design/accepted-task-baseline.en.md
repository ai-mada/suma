suma 1.0.0 · T-ACCEPTED-TASK-BASELINE-222. [Contract](../../contracts/accepted-task-baseline.md) · [Architecture](../architecture/accepted-task-baseline.md) · [Verification](../quality/accepted-task-baseline-verification.md).

Open the existing development baseline panel of an unstarted task. Choose an accepted task candidate or a composed result. Explicitly select the source task and producer, inspect its task version, full commit and exact run/attempt link, then give a reason and acknowledge this concrete input. Multiple producers are separate choices; none is selected automatically.

The original options endpoint exposes an explicit can_bind_baseline fact under current authorization. Its 200-item limit is disclosed. Composition can_create is not binding authority, particularly when replacing an existing baseline. The original dual-version command, operation receipt, code-input broker and independent worktree remain the only path.

Source, target, qualification, actor/API and input generations invalidate old acknowledgements. An uncertain write keeps its exact route/body/key even after the source disappears from current options. Refresh is a read and does not issue another write. The server revalidates current acceptance and same-commit tests from a different Worker; the browser cannot grant access by submitting a SHA or Review identifier.

Reuse existing components, 44px targets, keyboard focus and narrow layouts. Binding fixes code input; it does not start a task, inherit tests or accept new work. New code must be independently tested and reviewed. Real provider, multihost and complete platform acceptance remain separate evidence.
