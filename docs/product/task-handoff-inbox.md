# 交接请求进入个人收件箱

T-HANDOFF-INBOX-148，速码初始产品1.0.0。状态：实现与定向检查中，最终Git交付和GUI验收尚未完成。负责人：任务协作／通知／前端交互及主集成，分工见[合同](../../contracts/task-handoff-inbox.md)。本页说明产品行为，不作为验收证据。

用户向明确的项目人员发起责任交接，对方从个人收件箱打开准确请求，再独立决定是否接收。通知、责任变更、工具执行和正式交付验收分别保留自己的事实。

## 发起请求与真正接收

| 动作 | 产生的事实 | 不据此推断的结果 |
| --- | --- | --- |
| 发送交接 | 保存待接收请求，并在原事务内通知原接收人 | 任务负责人未改变，没有新执行或正式验收 |
| 接收职责 | 当前接收人明确确认后，变更负责人，任务回到进行中，并记录独立的任务分配事件 | 原测试或Review不因此变成新的交付验收 |
| 退回／撤回 | 原请求保留终态与决定说明 | 不转移负责人，不删除请求通知 |
| 打开请求 | 按准确ID读取当前有权查看的交接 | 不自动已读、接收、派发或批准 |

新交接、待接收槽位、个人请求通知、活动及原操作回执同事务提交。任一步失败全部回滚；同一原操作恢复不会重复创建通知或消耗新的通知序号。

接收后产生的任务分配通知与先前请求通知独立。请求通知仍可查看或由本人管理已读／归档，不因交接结束被删除，也不被自动标为已读。

## 从收件箱打开准确请求

1. 在当前项目个人收件箱看到“有人请你接收任务责任”。只有正式来源仍可读且绑定一致，才显示当前任务和打开入口。
2. 明确打开请求，沿原离开保护进入任务详情，并定位对应交接卡片。普通任务详情仍默认收起交接区。
3. 准确请求通过独立读取加载；即使不在当前20条交接记录内，也不需要反复加载更早记录。
4. 查看接收人、说明、状态及按需展开的固定依据；当前允许动作由服务端重新核对。
5. 明确选择接收、退回或撤回，检查当前版本并提交。打开、定位及读取不改变通知状态。

历史已接收、已退回、已撤回请求仍可准确读取，但历史状态不会恢复旧操作权限。来源缺失、损坏或绑定不一致时，保留私人通知和已读／归档事实，隐藏任务内容与跳转；读取故障应明确报错。

## 接收责任的影响

接收须由原接收人以当前项目写资格操作；原依据、接收人员及可选团队仍需有效。用户必须明确确认负责人变化，以及已验证交付和下游结果失效的影响。

原运行、测试、审查及交接历史保留。接收职责不自动执行工具，也不替代正式Task Review；正式验收仍按原质量门禁独立进行。

退回和撤回沿原角色权限完成并填写原因。依据已经过期时，不得借退回或撤回把旧工作重新变成当前有效交付。

## 草稿、版本与失败恢复

发起草稿保存接收人、可选团队、交接说明和任务版本；决策草稿独立保存准确请求、动作、说明和交接版本。两部分按人员／组织／项目／任务隔离，只保存自己的输入，不缓存来源历史正文。

语言切换、读取失败、定位其他请求或刷新不应清空未提交文字。只有已确认原回执对应的草稿部分会被清理；另一部分或后来改写的内容继续保留。

采用当前任务版本与采用当前交接版本是明确操作，不因刷新自动替换。采用新版本后重新确认接收影响。准确读取失败或失去资格时，不能退回旧分页记录继续决策。

结果未知时保留原账号、范围、版本、操作标识及原JSON，恢复同一个原操作。重新填写或采用新版本是新决定，不能冒充原回执恢复。

## 权限与易用性

当前调用者收到401／403／404时隐藏受保护信息和操作入口；旧调用者或旧身份的迟到响应不能恢复它们。恢复权限后重新打开任务详情，不能依赖旧卡片继续提交。

中英文使用同一组词条，姓名、说明和依据保留原文。支持键盘打开、定位焦点和操作；按钮、下拉框及依据展开入口采用至少44px高度，准确卡片避开固定页头。实际中英、窄屏、键盘及触控表现须独立GUI验证。
