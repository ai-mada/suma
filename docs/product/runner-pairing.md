# 远程执行节点配对

T-RUNNER-PAIRING-184，速码 suma 1.0.0。项目管理员可以在浏览器批准另一台机器的准确凭据摘要，由目标机器自行保管秘密并采用已批准的项目身份，无需手填 Worker ID 或粘贴 token。依据[合同](../../contracts/runner-pairing.md)；验收结果见[专项报告](../quality/runner-pairing-verification.md)。

## 使用流程

1. 在原 Worker 登记窗口展开默认折叠的远程配对入口。当前项目自动固定；明确创建一个十分钟待办，每项目最多八个未到期、未结束待办。
2. 明确选择 PowerShell 或 Bash，核对并复制不含凭据的命令，在目标机器执行。Runner 先把随机 token 存入系统凭据库，再持久化公开 identity 和原请求，随后提交摘要。机器名称由本机自报，不能单凭名称认定机器身份。
3. 浏览器刷新同一待办，核对机器名称和完整摘要指纹。当前项目管理员按当前版本明确批准；服务端才会登记 `remote-` 节点和原二十四小时独立 Runner Grant。
4. 目标机器使用原 token 查询原结果。只有当前 Grant 和准确 Worker 仍有效，才保存批准元数据并报告 `prepared` 后退出。浏览器可刷新原 Worker 列表，并按准确 Worker 继续配置。
5. 后续通过 `--identity PATH` 明确执行原单次 `--report-tools`，或单独启动原 Worker。配置复用／暂停登记与启用继续使用原流程，需要独立确认。

配对本身不报告库存、不领取任务、不发任务心跳、不启用工具，也不运行任务。`approved` 是历史批准事实，`prepared` 是本机完成身份准备；两者都不表示持续在线。库存新鲜、持续运行、配置启用、模型登录、独立测试和人工验收各自需要证据。

## 原件与恢复

控制面地址由服务端运营配置固定，保留准确路径；远端使用可达 HTTPS，回环 HTTP 只适用于本机。后续批准、机器提交或状态读取发现控制地址变化时明确拒绝，不自动跟随新作用域。身份文件中的控制面、项目、配对和原操作不能被另一次配置覆盖。

响应未确认时，浏览器先恢复原正文和操作键；目标机器重启同一配对命令，读取原 identity 和系统凭据。创建恢复原 `waiting` 回执，批准恢复原批准回执；之后另行读取当前状态。不能换 token、摘要、机器或操作键来掩盖未知结果。

期限由数据库时间判断。页面显示绝对到期时间和服务端状态，不用客户端时钟制造倒计时或批准资格。待办过期不撤销已经发行的独立 Grant，但过期／撤销的 Runner 凭据不能通过旧批准重新恢复。续期或重新配对属于后续明确授权。

## 凭据与当前状态

使用固定 `github.com/zalando/go-keyring v0.2.6`，适配 Windows 凭据管理器、macOS Keychain 和 Linux Secret Service。公开 identity 不含 token；无安全后端、原 secret 缺失或摘要不符时拒绝，不能降级为明文文件。SDK 提供三种系统实现不代表三种系统均已实机验收。

已取得后端受控 HTTP／SQLite、当前身份、CAS、原回执和并发上限等定向证据。Root 本轮 Windows 真实系统库与 HTTP 检查待集成至专项报告，不能由组件或注入测试替代。其他平台系统库、物理多机、完整登录旅程、厂商工具／模型、安装与生产仍需独立验收；原三十一项／P0–P7 完整目标继续。
