# 向原执行追加指令

状态：suma 1.0.0 当前实现中；需求：T-TURN-STEERING-188；负责人：主集成／控制面／Runner／Web。依据：[领域合同](../../contracts/turn-steering.md)、[架构与 AI SOP](../architecture/turn-steering.md)、[交互设计](../design/turn-steering.md)、[English](../en/turn-steering.md)。实现与验证结论分别记录，本文不宣称验收通过。

用户在任务讨论中保存一条本人消息后，可以明确把这条原文追加给同一任务正在运行的 Codex 回合。普通评论仍只是讨论；点击入口、核对原文和准确执行目标、单独发送后，平台才登记追加指令。用户不必复制终端协议，也不必另建任务。

## 旅程与范围

保存本人 human 消息 → 打开该消息的“追加到原执行”入口 → 读取当前可用目标 → 选择准确运行／节点／尝试 → 预览完整原文 → 明确发送 → 查看保存与投递事实 → 原执行按原流程形成代码候选、独立测试和人工验收。

本阶段支持原生 Codex `turn/steer` 文本输入。它使用原进程、原 thread 与原 turn，不创建新 turn、不恢复旧 thread，不替换原计划或验收基线。原工具工作区、模型、预算、工具授权、知识和技能来源保持各自约束；该动作不新增授权。稳定文本追加不依赖 T187 的实验性问答开关，也不增加桌面配置开关。

可发送条件由当前服务端共同判断：

- 当前浏览器账号拥有项目写权限，且消息是本人已经保存的 human 消息；API、Runner、助手消息不能冒充本人发送。
- 原任务尚未正式验收，准确原运行、节点、attempt／fence、Worker、派发与配置来源仍具备当前资格。
- 原 Runner 已收到原配置和 `turn/start` 的准确 ACK，并且原 turn 未停止或关闭；节点显示运行中、历史 `run_id`、会话记录 active 均不能单独证明可发送。
- 当前机器身份、库存、Grant、租约、暂停与预算条件满足原执行边界。

每个 session 对同一消息只登记一次，最多 32 条。正文与原讨论共用 32,000 UTF-8 字节／8,000 Unicode 字符上限，须为有效 UTF-8、非空白且不含 NUL；其余字符经 JSON 完整保留，不裁剪。继续补充应先保存另一条消息。秘密、凭据和密码不通过本入口输入。

## 用户可见事实

| 事实 | 含义与后续动作 |
|---|---|
| 指令已保存 | 平台已保存原消息与目标绑定；执行器可能尚未读取 |
| 执行器已观察 | 原 Runner 已看到这条指令 |
| 开始写出 | 原生写入已经开始，不能再按新指令重发 |
| 已完整写出 | 原协议帧写出完成；等待原生响应 |
| 原生已接受 | 准确原请求得到同一 turn 的接受响应；不证明模型已遵从 |
| 原生已拒绝 | 原请求明确被拒绝；如实保留拒绝事实 |
| 结果待核对 | 写入或 ACK 无法确认；保留原意图，只核对原操作 |
| 原回合已关闭／未送达 | 不再新写；没有派发的指令不显示成已接受 |

平台保存、原生接受、执行完成、代码候选、同提交独立测试、人工验收与部署是独立事实。追加指令接受后，任务仍沿原质量和验收流程推进。

## 验收条件与边界

1. 发送准确本人已保存消息，不允许客户端自填替换正文、原生地址或模型配置；目标绑定准确同任务当前原回合。
2. 版本变化、过期、停止、撤权及执行身份漂移阻止新发送；已经提交的同一操作，在当前人授权通过后可恢复原回执。
3. 响应丢失时保留原消息、旧 session、原执行 tuple、原 body 和操作 key；同 key 不同 body 拒绝。未知原生写入不自动重发、换 key 或另开回合。
4. 原生关闭先于写入时不发送；写入已经开始时保留迟到事实。普通与 Pool 路径使用一致语义。
5. 中英文、390px 窄屏、键盘、源切换与迟到响应使用原讨论组件和恢复保护；一个入口只加载所选消息，不给每条讨论轮询。

当前实现与限定检查、真实 CLI／受控模型、授权 HTTP／SQLite、合成组件界面及真人验收需分别留证。其他工具协议、旧隐藏会话恢复、真实厂商模型、物理多机、其他数据库、跨平台安装及生产接受各有独立验证范围。完整 31 项需求、P0–P7、58 项限定／34 项待交付／92 项总账继续，原 T171 显式 GUI 停止缺口保留。
