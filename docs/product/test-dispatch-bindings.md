# 开发与独立测试工具的明确派发

速码1.0.0 · T-TEST-DISPATCH-BINDINGS-216。领域合同见[开发与独立测试的明确派发绑定](../../contracts/test-dispatch-bindings.md)，实现细节见[设计说明](../design/test-dispatch-bindings.md)。完整31项需求及P0–P7继续推进。

## 用户目标

在原任务派发页选择开发工具后，可以为本次候选关联的测试节点明确选择测试工具及执行节点，不必为一次派发修改、重新发布工作流。选项默认折叠，保留原页面的任务、流程、模型、预算和正式预览操作。

未选择覆盖时，继续使用原发布定义。界面应将其标为原定义或未确认，不能将“保留原定义”描述成已核实的独立测试。

## 操作步骤

1. 选择当前任务、已发布流程版本、开发节点和开发工具。
2. 按需展开“本次独立测试工具”，只对当前开发节点的关联测试明确选择覆盖。系统不默认采用第一个工具。
3. 核对测试节点、工具版本、Worker及配置摘要。目录用于发现候选。选择后检查执行路由、流程节点、档案版本与独立性，并在当前行显示结果。分页外已选项保持可见。
4. 创建原正式预览。预览只修改本次流程副本，并冻结明确选择的节点、工具ID、版本、SHA、Worker和命令。
5. 审阅预览后沿原操作启动。工具、库存、权限、执行路由或任务依据变化时，重新核对并预览，不自动换用新的工具版本。

测试工具必须已启用、库存新鲜，使用可写的固定命令和完整JUnit报告协议，且Worker与开发Worker不同。同一Pool的不同槽位不代表不同Worker。选择配置通过后，执行仍需证明测试使用的是开发节点当前候选的同一提交。

## 恢复与验收

创建或启动结果未确认时，恢复原请求正文和操作key；不重新获取版本后提交另一操作。切换账户、组织、项目、任务、流程、开发节点或开发工具，会使旧选择失效，迟到响应不能恢复它们。

存在明确测试覆盖或选择尚未确定时，智能推荐的新分析和新采用不能忽略这些选择创建计划，应引导用户使用正式预览。已有推荐待确认操作仍可按原正文和key核对、恢复，保留原离开保护。

验收区分配置资格、代码执行、同提交独立测试和人工决策。代码验收必须为每个实际产出节点找到准确来源、当前attempt/fence及证据摘要一致的成功测试，并核对不同Worker；仅提交SHA相同或页面显示测试成功不足以证明独立性。原DAG候选固定、数据库来源配对、测试报告及人工Review权限继续生效。

## 模块与AI SOP

工作台负责明确选择与当前来源保护；原TaskDispatch服务负责冻结和原子准入；Runner及原质量领域负责候选、测试报告与验收证据。选择时检查复用预览的绑定规则和执行路由，正式计划仍由原命令创建。

AI协作时应先读取当前任务和准确流程节点，显式选择所需测试覆盖，审阅原预览，再恢复或启动同一操作。不得发布一个临时流程来绕过工具资格、用相同Worker伪装独测，或把配置就绪当成代码已验收。阶段实际检查及证据由最终质量报告记录；本文不预先声明真实厂商、模型、多机或完整平台验收完成。

阶段结果已记录于[限定验证](../quality/test-dispatch-bindings-verification.md)：真实Git／另一Worker同提交JUnit及夹具Review通过；UI只提交预览，启动与Review由Go宿主完成。SQLite取消恢复采用官方驱动修复，完整服务包／厂商模型及正式客户签署仍有各自验收边界。
