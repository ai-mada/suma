# 项目知识、记忆、规范与技能：产品需求

状态：T-P4-015 限定范围本地已验证；完整平台继续实施。日期：2026-10-25。
负责人：知识领域与平台集成。关联：[统一合同](../../contracts/project-knowledge.md)、[领域架构](../architecture/project-knowledge.md)。

## 用户目标与范围

把分散在文档、需求、任务和问题中的项目约定沉淀为可审阅的知识，并明确采用到开发任务。
用户能看清“最新草稿”“当前发布”“来源已变化”和“已用于哪份固定上下文”的区别。
本阶段共用一个“资料 → 项目知识”子页，通过类型筛选承载记忆、规范、技能，不增加三个顶层菜单。

| 类型 | 用途 | 本阶段实际边界 |
|---|---|---|
| memory／记忆 | 保留决策背景、约定和经验 | 有来源或人工输入的项目文本，不是自动模型记忆同步 |
| spec／规范 | 复用验收约束与研发标准 | 已审阅的正文与引用，不替代需求基线或实际质量门禁 |
| skill／技能 | 复用操作步骤与开发 SOP | 文本工作说明，不安装插件、执行脚本或授予工具权限 |

## 导入本地技能

在项目知识点击「导入技能」，选取 `SKILL.md` 后即可核对和编辑标题、说明及正文。保存后在当前项目得到可审阅的技能草稿。读文件失败或校验不通过时可以重新选择。需要技能包里的附加文件、许可或环境信息时，可同时查阅原技能包。

桌面和窄屏共用现有编辑器及关闭确认。可通过键盘选择文件和提交草稿，导入状态和错误使用当前工作台语言。

### 命令行预览与保存

以下 PowerShell 7 示例使用项目标识固定草稿的保存范围。第一条命令生成本地 JSON，核对或编辑完成后，再用当前有效的 `SUMA_TOKEN` 执行第二条命令。

```powershell
suma --project PROJECT_ID knowledge import-skill --file ./SKILL.md > skill-draft.json
suma --control https://suma.example --project PROJECT_ID knowledge create --file skill-draft.json
```

创建命令返回草稿 ID。若写入结果未知，保留同一项目、调用身份和原 JSON，再使用相同命令核对结果。对内容的后续编辑沿现有草稿修订进行。

## 导入 HelixHarness 规范

在「知识空间 → 项目知识」选择「导入 HelixHarness 规范」，打开仓库中 `docs/specs/active/<slug>/spec.md` 或 `docs/specs/completed/<slug>/spec.md`。检查预填的标题与正文，按需补充说明，再保存到当前项目。文件无效时可直接重新选择，关闭已编辑的草稿前会提示保留或放弃。

命令行可在本机生成同样的草稿。检查 JSON 后，才执行现有创建命令。

```powershell
suma --project PROJECT_ID knowledge import-helix-spec --file "./docs/specs/active/feature/spec.md" > helix-draft.json
suma --control https://suma.example --project PROJECT_ID knowledge create --file helix-draft.json
```

有审批权限的成员可随后发布固定修订。团队在任务派发时明确选择该修订。需要核对原仓库、任务清单或验收报告时，可在草稿摘要中手工备注出处。上游规范流程见 [HelixHarness 示例](https://github.com/didi/helixharness/blob/main/examples/README.md)。

## 角色与权限

| 操作者 | 可执行操作 |
|---|---|
| 有项目读取权的成员 | 当前列表、详情、草稿和不可变历史；不能因读取获得写入权 |
| 有 ProjectWrite 的浏览器成员／项目 API | 创建、提取和完整修改草稿，携带稳定 key 与版本 |
| 有 BrowserProjectApprove 的真实浏览器成员 | 审阅并明确发布／退役；API、Runner、Agent 不能代为批准 |
| 项目 Agent | 通过专用工具读取明确引用的当前发布快照；不能读取管理页或新草稿 |

团队归属不授予项目访问；凭证、项目权限与角色均由服务端当前状态核实。
退出、撤权或过期后，成功回执也不能代替当前权限。

## 核心用户旅程

1. 进入项目资料，筛选已有知识或创建 manual 草稿；编辑类型、标题、说明与正文。
2. 需要提取时选择同项目正式来源及版本，提供原文片段，或以空片段选择完整可见正文。
3. 生成 `extractive` 草稿，核对原文、出处和方法，再人工编辑；界面不把文本提取称为模型总结。
4. 审阅者发布当前草稿，详情展示新的发布修订、摘要及来源；旧草稿和作者时间仍可从历史追溯。
5. 在任务派发中明确选择已发布知识，以发布标题、说明、修订和摘要核对，进入固定计划预览。
6. 启动前再次核验发布与来源；允许后将正文和来源凭证固定到运行，不随后续编辑漂移。
7. 后续修改产生新草稿，旧发布仍可用；明确新发布／退役或来源变化使未启动计划要求重新核对。

后端与合同已有对应定向通过证据；上述完整界面旅程由平台集成验证，不以构建或单元测试替代实际浏览器结论。

## 交互与可读性

- 列表展示当前类型、状态、最新摘要、是否另有草稿及发布资格；详情分开展示草稿与发布正文。
- 派发选择使用 `published_title/published_summary/published_sha256`，不以新草稿标题冒充批准内容。
- 来源可以回到正式对象；历史按需展开、分页读取，保留当时原文和版本，不用全量历史阻塞首屏。
- 空态给出创建／提取入口；失败、版本冲突、无权限与未知回执保留用户正文和原操作身份。
- 中英文只改变产品文字和格式，用户正文、来源片段、ID、修订、摘要及执行证据保持原样。
- 窄屏提供完整列表与详情操作，表单和历史展开可由键盘操作；焦点与刷新位置由工作台路由承载。

## 明确限制

| 输入／读取 | 上限与行为 |
|---|---|
| 标题／说明／正文 | 200／1,000／16,000 UTF-8 字节；非空正文，超限明确拒绝 |
| 来源 | 最多 8 项；仅 documents、requirements、tasks、issues；片段必须是可见正文中的连续原文 |
| 文本提取 | 至少 1 来源；不截断原文；完整来源过长时要求选择更短片段 |
| 列表 | q 最多 200 UTF-8 字节，支持 kind／state／q；默认 50、最多 100 条 |
| 修订历史 | 默认 20、最多 100 条；游标绑定知识、项目和租户 |
| 任务上下文 | 最多 16 个引用；任务、需求、知识和流程指令的完整 goal 合计最多 32,000 UTF-8 字节 |

消费时 `ProjectKnowledgeContextSource` 仅传来源类型、ID、版本、标题和摘要，不重复 quote；完整引用仍留在修订／历史中，批准摘要继续绑定完整修订，正文和验收条件不静默删减。
“当前可采用”只表示发布与来源依据有效，不自动证明文本正确、模型效果、执行成功或需求验收。

## 未知回执与恢复

提交结果未知时，恢复区保留原 key、完整正文、方法与路径，并按账户／组织／项目隔离；保留请求期间不开始另一份命令。
恢复必须使用原操作身份，不能用新 key、后来读取的版本或另一个账户的上下文冒充重试。
收到成功回执后重新读取当前列表与详情：回执可能是历史快照，其 version 不能直接用作下一命令的 CAS。
如果恢复记录不可读取或身份不匹配，保留草稿并核对正式数据与活动；不能把“未收到响应”直接当作“没有执行”。

## 功能验收标准

- 发布前后与再次编辑后，草稿和批准正文可区分；历史修订内容不被覆盖。
- 错误项目、API 批准、Agent 管理页访问及撤权后的 fresh／replay 均被拒绝。
- 来源片段失配、版本变化、归档或删除阻止新发布／新派发，旧运行证据保留。
- 同 key 同正文恢复原操作，内容不同返回冲突；重放资格按历史发布自身重新投影，不混入新正文。
- 派发使用批准快照且维持 32,000 字节预算；16,000 字节提取正文不因重复 quote 成倍消耗上下文。
- 中文／英文、刷新、分页、冲突与键盘操作取得实际界面证据后，才能将对应体验记录为通过。

外部记忆系统同步、语义索引投影、模型提案、跨项目共享与可执行插件技能仍是完整平台待办。
