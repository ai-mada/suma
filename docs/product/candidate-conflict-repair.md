## 用户要完成的工作

031 合成遇到真实 Git 冲突时没有可封存候选。用户需要保留原失败，将原准确来源、顺序和冲突作为修复输入，交给明确授权的原生开发工具，产出自己的候选、独立测试和 Review。

在原合成详情展开“准备冲突修复”，先查看原运行已记录结果，再查看当前修复资格。原失败事实不因来源后续失效或修复成功而改写。只有路径列表、缺少完整 Git 冲突依据的旧失败可读，但不可用来授权修复。

填写新任务标题、修复说明及1–16项验收标准，明确选择固定流程、产出节点及当前已启用的原生工具。优先级可省略，服务端在操作摘要前归一为 medium；负责人可省略，仅在当前账号唯一匹配活动项目人员时跟随该人员，否则保持未分配。“创建修复任务并预览”原子创建一项新未开始任务和新的 CandidateCompositionPlan；不会创建运行。

同一原失败执行的冲突身份保持不变，另一个操作编号或编辑原任务不会创建第二项修复。新操作仍需当前完整依据摘要进行版本核对；找回已有修复不等于批准使用过期来源。

打开新任务的准确预览，核对原冲突和全部有序来源、开发工具版本、固定路由，再单独勾选确认并启动。可信宿主保留2–16份来源，原生工具按固定 Git 冲突逐项解决并继续后续来源；不能丢弃来源、把冲突标记当成功或用原来源测试代替新候选测试。

待启动修复预览过期后，填写理由并明确“重新核对并延长预览”，重核同一任务、冲突、来源、工具及路由后只延长有效期和更新计划版本。不会重建任务或运行，也不更换固定工具、流程或原依据；更换这些定义仍需后续独立设计。

## 交付与权限边界

修复任务运行、封存候选、独立正式测试、明确 Review、目标集成与下游基线绑定是独立事实。原失败计划不会变为 accepted。验收后的新修复计划沿用既有合成 ID 基线绑定路径，不增加混合来源或“最新候选”选择规则。

工具必须由 Runner 管理员明确设置本地 `native_workspace.conflict_repair`，经真实能力探测、导入及启用后声明 `suma.candidate-conflict-repair.v1`。浏览器模板和复选框不会修改远端 Runner 策略，也不证明模型或厂商可用。

所有新使用重核当前项目权限、来源验收、工具版本、路由及准确 attempt／fence。来源漂移阻止新执行和批准，已发生的原失败或输出仍保留。

## 恢复与体验

面板默认折叠零读取；技术哈希与原件默认披露。系统标签成对中英，任务文字、代码、路径、修复说明和不可变证据保持原文。

409保留草稿并明确读取最新事实；未知创建沿用原 path／body／key找回原新任务，不重复创建或启动。401／403立即隐藏受保护事实并阻止写入。账号、组织、项目或原计划切换隔离旧状态并中止读取。

已知失败只有在固定节点声明幂等、后继尚未执行且当前来源／工具／权限仍有效时，才允许人工在同一运行内重试，生成新的 attempt／fence并保留旧失败。未知结果必须先核对原操作，不能自动重跑模型或另建任务。

原生记录中的“合并完成后无额外编辑”指相对全部来源已处理的合并前缀没有额外编辑；候选相对管理员锚点仍可能有文件变化。此提示仅用于准确匹配当前工作区的完整修复依据，不表示测试或验收。
