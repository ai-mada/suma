# 组织、团队与项目权限

实现日期：2026-10-23。身份和权限来自服务端持久化成员关系；组织管理接口不接受 API、Runner 或 Agent 项目凭证。

## 组织与成员

浏览器用户可以列出自己加入的组织、创建组织和切换组织。创建组织使创建者成为新组织 owner，当前会话仍停留在原组织；切换需要目标组织的现存成员关系，并签发该组织的浏览器会话。用户可以在多个组织中拥有不同角色，组织之间的项目始终隔离。

组织角色为 owner、admin、member。owner/admin 管理邀请、团队和组织内的显式项目授权。admin 不能修改 owner 或将任何人提升为 owner。提升所有者必须由 owner 在成员 PATCH 中显式提交 `action: "transfer_owner", role: "owner"`；该动作新增一位所有者，原所有者如需交接后退出，可以再降级或移除自己的成员关系。降级或移除不得使组织失去最后一位 owner。

成员 PATCH 支持 `action: "remove"`。移除在同一事务内删除组织成员关系和组织内项目授权，撤销此组织的浏览器及项目凭证，将团队中的人类成员关系标为 removed，并撤销被移除成员尚未使用的邀请。其他组织中的成员关系和会话不受影响。

## 一次性邀请

`POST /organization/invitations` 接受邮箱、admin/member 角色及可选的项目授权列表；邀请不能授予 owner。项目必须属于当前组织，授权角色必须是 admin、reviewer、developer 或 viewer。创建时显示一次随机邀请密钥，数据库只存其 SHA-256 摘要；24 小时过期。列表、活动和操作回执均不含密钥。相同操作重放仅返回原邀请元数据和 `token_revealed: false`，密钥遗失时应撤销并重新邀请。系统不发送邮件。

`POST /auth/invitations/accept` 是公开的显式接受操作，必须提交邀请密钥、匹配的邮箱、姓名、密码及操作标识。密钥与邮箱经过常量时间比较，邀请状态、有效期、邀请人现存管理权限和全部项目范围会重新检查。新用户在同一事务中创建账号、组织成员关系、项目授权、已使用的邀请状态和浏览器会话。已有账号必须证明原密码，其姓名和密码不会被邀请覆盖；已在组织中的账号不会被邀请降级或升权。

已接受、已撤销和已过期的密钥均不可再次接受；重复相同操作标识也不会重用已接受密钥。如果接受请求的结果未知，应尝试普通登录，不能通过重复接受改写账号。事务失败不会消耗邀请或留下部分账号和授权。

## 组织团队

团队包含名称、描述、active/archived 状态和独立版本。团队角色为 lead、member、observer，用于组织结构，不会隐式授予项目权限。

人类成员的 `resource_id` 必须是当前组织真实用户的 ID，`project_id` 留空。agent/tool 成员必须同时指定 `project_id`，并引用同组织同项目中种类相符的既存项目资源记录；资源登记不代表模型、外部账号或工具已实际连接。不存在的用户、跨组织资源和种类不匹配的资源均拒绝写入。归档团队只允许移除成员。

团队成员身份组合固定为团队、resource_kind、resource_id、project_id。首次添加使用 `expected_version: 0`，更新和移除使用当前成员版本。移除保留稳定 ID 和递增版本的 tombstone；重新添加必须使用该版本。GET 返回 active 与 removed 状态，界面应按状态展示。

## 项目授权

只有组织 owner/admin 或该项目的显式 admin 可以读取和治理项目授权。项目 admin 只能管理自己有权管理的项目，不能修改组织 owner/admin 的项目授权。普通成员的项目读、写和审核能力完全由该项目的实际授权决定；viewer 只读，developer 可以写，reviewer/admin 可以进行审核。

组织 owner/admin 通过组织角色继承组织内全部项目权限；显式项目授权的缺失或撤销不会撤销这种继承权限。组织角色变更和成员移除由服务端重新检查，旧会话中缓存的角色不能恢复权限。

项目授权首次创建使用 `expected_version: 0`，修改/撤销使用当前版本；`action: "remove"` 撤销授权及该用户绑定该项目的独立凭证。授权列表包括带 `status: "removed"`、空 role 和递增 version 的撤销记录，用于安全重新授权；该记录不授予任何权限。重新授权必须使用撤销记录的当前版本，防止移除前的旧创建请求重新生效。

## 一致性与已验证范围

治理写入要求 8–128 字符的稳定 `idempotency_key`，版本必须是非负整数。操作回执使用 `@organization` 范围，绑定操作者、操作类型、对象和完整请求；同标识改写内容返回冲突。每次写入和重放都重新加载真实成员权限。组织写锁在事务读取角色和版本前取得，保证所有者保护、邀请消费及授权修改不会交错绕过校验。

`internal/platform/governance_test.go` 使用真实 SQLite、正常浏览器初始化和邀请创建的真实账号，覆盖新账号、已有账号密码证明、多组织与多项目隔离、一次性邀请及密钥保护、过期/撤销、团队真实资源、项目 RBAC、旧版本冲突、撤权和受限凭证。并发接受和所有者降级使用两个独立数据库连接验证，不依赖内存模拟。

本轮实际执行 `go test ./internal/platform -run '^TestGovernance' -count=1`：15 项治理测试通过（3.541 秒）。最终执行 `go test ./... -count=1`：全部 Go 包通过，platform 8.334 秒、runner 20.175 秒。两个独立连接的接受/所有者降级竞争另重复 3 次，均只允许一方成功，另一方明确返回 409。

以上命令的进程环境为 `GOCACHE=D:/codes/ai-dev-os/suma/.cache/go-build`、`GOTMPDIR=D:/codes/ai-dev-os/suma/.cache`、`TEMP=TMP=D:/codes/ai-dev-os/suma/.cache/test-tmp`。未修改全局环境，未清理共享缓存。测试还证明：移除组织成员会推进已撤销授权的版本，旧授权请求不能在重新加入组织后恢复生效；接受回执不包含密码派生的快速校验摘要，账号密码仍只使用原有慢速 KDF 验证。

SQLite 为本轮实际验证后端。PostgreSQL/OceanBase 的兼容 DDL 和查询路径已实现，真实集群的迁移、并发、故障恢复和运维验证仍待执行。邀请不发送邮件，不包含 SSO、密码重置、邮箱验证或组织付费席位系统。
