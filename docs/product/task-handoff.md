# 团队任务交接 PRD

状态：T-P4-022 本地实现与必要验证完成。负责人：任务协作域。关联[合同](../../contracts/task-handoff.md)、[架构与 AI SOP](../architecture/task-handoff.md)。完整平台目标保持进行。

## 用户目标

项目负责人将一项任务交给另一位真实项目人员；可明确绑定其所属团队。接收人核对固定依据、影响和说明后接收或退回，发起人可撤回未处理提案。每个任务只有一个待接收交接，历史按正式时间与 ID 分页。

操作入口位于任务详情“团队交接”，默认折叠，展开后才读取。创建仅选择服务端返回的有效接收人、可选团队与交接说明；没有合格人员时引导到项目人员资源登记，不自动创建账号或授权。发起后显示待接收对象、说明、当前阻断原因与可用操作；原始依据按需展开。

## 接收规则与影响

“已接收交接”是责任变化，不是任务验收通过。接收前必须勾选影响确认：原子更新项目资源 owner_id、增加任务版本、恢复 in_progress，并使旧派发／验收资格和相关下游资格失效。原执行、代码候选、测试与评审作为历史保留，不自动执行、重试或验收。

发送时固定任务、需求、原负责人、执行与交付依据；接收时重新核对。目标资源、账号权限、团队或其成员资格变动也阻止使用旧提案。活跃执行、未知结果或补偿未收尾时先核对原执行。依据变化不妨碍有权限者退回／撤回旧提案。

任务 owner_id 是项目成员资源 ID，账号 user_id 才决定谁能接收。当前收件资源限定已启用的 human，绑定真实账号且有项目写权限；团队身份使用该账号的有效 member／lead 资格。agent／tool 仍由现有任务派发管理执行身份和版本，不使用工具目录冒充人工责任确认。

## 交互和验收条件

- 中文与英文文案、错误、状态、时间和数字遵循现有目录；任务内容、交接说明、理由、ID 与摘要保持原文。
- 只有服务器当前允许的动作可见；每次写入仍由后端重验，不依赖按钮隐藏。
- 接收需明确影响确认；退回和撤回需理由。冲突保留草稿，重新读取后由用户决定；结果未知必须恢复原操作，不生成新操作 ID。
- 切换账号、组织、项目或任务取消旧读取并隔离迟到结果；折叠不在后台新建工作或轮询。
- 接收成功后刷新正式任务与交接历史；显示新的负责人／版本，不能将其显示为业务完成或重新验收。

专家组代理自动交接、跨组织协作、自动模型决策与目标仓库合并仍是后续完整范围。当前功能不声称这些已实现。
