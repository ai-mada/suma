T-MULTICA-FOLLOW-154，速码1.0.0。状态：限定实现已通过独立SQLite／Windows Electron软件离屏的实际HTTP与GUI验证，完整平台未验收。接口与边界以[本人任务关注合同](../../contracts/task-subscriptions.md)为准。它继续[Multica优先级第二切片](../integrations/multica-priority-map.md#原三个切片首片150已限定交付)的M09／M27范围，完整平台58项限定实现／34项待交付／92项总数不变。

## 用户目标与范围

用户在当前任务讨论入口旁点击一个关注按钮，接收此后正式保存的新讨论。新通知进入现有个人收件箱，打开准确原消息；取消关注只影响后续消息，已有通知继续保留。

当前浏览器人员和有权的当前用户API只管理自己的偏好。项目viewer可以关注可读任务，无需任务业务写权；关注不授予发帖、开发、执行或验收权限。接收账号由认证推导，请求不能替别人关注，不接受Runner、Agent或Pool身份。不按负责人、团队、历史提及或打开页面自动建立关注，不公开其他关注者名单。

| 用户动作 | 保存的事实 | 用户看到的结果 |
| --- | --- | --- |
| 首次读取 | 没有个人行时返回version0、未关注、空更新时间；不创建记录 | 读取成功后显示“关注” |
| 明确关注 | 按本人当前版本保存following=true | 显示“已关注”，随后提交的新讨论可产生通知 |
| 明确取消 | 保存following=false，保留个人行和单调版本 | 不再接收后续关注通知；已有通知仍可打开 |
| 打开通知 | 当前授权下准确读取原任务／消息 | 聚焦原消息；不自动标为已读 |

只有真实偏好变化才递增版本。已为目标状态的合法命令不空更新；对从未关注的任务取消，可以返回无副作用的version0回执。通知的已读、归档与恢复仍使用原收件箱的独立操作。

## 哪些讨论会通知

接收集合取原消息提交时全部已关注且当前仍有项目访问权的账号，不截断为一页，也不在以后读取时补发历史消息。

| 正式来源／接收关系 | 结果 |
| --- | --- |
| 人员或用户API提交消息，接收人已关注 | 原消息事务保存task_followed |
| 人员／API作者自己也已关注 | 不额外通知作者 |
| 同一原消息已精准提及该接收人 | 只保留既有task_mentioned，不再增加关注通知；自提及原语义保留 |
| 平台最终assistant消息，完整绑定原回复与执行结果 | 在最终消息事务通知当前有效关注者，可包括已关注的请求人 |
| 模型流式片段、执行进度、工具日志、测试或验收状态 | 不作为讨论关注通知来源 |

消息、合法接收人的通知、私有来源关系和原回执同事务保存；任一通知投影失败，原事务回滚。重放原发帖／回复操作不重复通知，也没有独立的任意通知发送入口。

通知保存来源引用，不复制正文、任务标题或模型输出。当前授权及完整来源绑定成立时才显示当前任务并返回message_id；来源缺失或损坏显示“来源不可用”，不暴露正文或链接。后来取消关注不使旧来源失效，当前撤销项目访问权仍由原收件箱拒绝读取。

## 失败与原操作恢复

关注与取消均使用个人版本CAS和稳定操作标识。界面在发出前保存原调用者、任务范围、正文与key；结果未知时锁住切换并提供“核对原操作”。恢复必须使用同一正文与key，不生成第二次操作；存储不可用时不发送。

版本冲突先明确读取当前状态，再由用户决定下一次动作，不自动换版本重发。原回执只证明原提交，当前是否关注另读；刷新或当前值恰好符合都不能确认未知的原操作。用户、组织、项目、任务或API caller变化后隔离迟到响应；401／403／404清除受保护内容。

## 交互与交付边界

默认只有一个Bell按钮，文字、aria-pressed与可见焦点共同表达状态；读取未知时不能先显示为未关注。中文“关注任务／已关注”与英文“Follow task／Following”保持对应，窄屏自然换行。收件箱沿原入口显示“已关注任务有新讨论”，准确消息定位与已读操作分开。
