## 完整目标与领域边界

项目是权限与交付责任边界，子项目表达可管理的分工关系，应用是可独立构建、测试、版本和部署的产品单元。一个仓库可包含多个应用，一个应用也可能依赖多个明确授权的仓库来源。关系必须显式保存，不能用文件夹名称或字符串标签假装完整应用管理。

速码自身产品版本保持1.0.0；被管理应用的版本、代码提交、需求修订、迭代、部署批次和知识资产版本分别有独立语义。应用目录、依赖关系和版本集属于当前正式领域，不建立旧产品字段转换或双写兼容层。

| 领域 | 正式对象与责任 | 必要门禁 |
| --- | --- | --- |
| 项目与应用目录 | Project、Subproject、Application、RepositoryBinding、TeamOwnership | 当前租户／项目授权、无环父子关系、源代码范围明确、责任团队真实存在 |
| 需求与迭代 | RequirementRevision、Feature、ApplicationIteration、DeliveryScope | 需求与设计依据固定，可审阅拆解、任务分配和范围变更，不能无提示扩大已验收范围 |
| 依赖与影响 | DependencyObservation、DependencyRevision、ImpactPlan | 从固定代码提交解析，不执行不可信安装脚本；保存解析器版本／来源，人工校正需版本化，不确定关系明确标记 |
| 应用版本集 | ApplicationRelease、ReleaseSet、ArtifactManifest | 绑定准确代码／构建／应用配置及依赖版本，各应用测试证明独立有效，不能以某应用通过覆盖整个版本集 |
| 质量与问题 | Issue、Defect、TestPlan、TestCase、TestExecution、Repair、RegressionReview | 复现、环境、影响、责任、优先级、修复候选和回归证明可追溯；人工关闭与测试结果分开 |

## 缺陷全链路

支持手工、测试失败、运行故障和授权渠道采集问题，保留原始来源、复现步骤、环境、证据和影响范围。智能分诊产生可审阅的去重／归类／优先级／责任／修复建议，不把模型建议直接当作已确认根因或已解决事实。

正式流程应覆盖受理、分析、已确认、待修复、修复中、待回归、回归失败／通过、待验收和关闭／重新打开；项目可通过版本化流程配置裁剪，但每次转换须核验当前角色、预期版本、稳定操作和必要证据。拒绝、重复、延期与无法复现有明确决定及原因，不能通过通用状态编辑跳过回归和验收。

修复关联原问题、当前需求／任务、应用版本和准确代码候选。独立回归失败回到原缺陷并保留尝试；重复事件沿原来源去重，不能无限创建新需求。主动预警、站内通知、外部消息及自动修复分别受权限与策略约束。

## 依赖识别与关联迭代

按实际技术栈优先复用成熟解析器，从固定代码中的包清单、模块声明、构建文件、部署配置和明确接口合同识别应用依赖。每条观察保存仓库／提交／文件／定位／解析器版本／关系类型／版本约束和可信程度；解析、补充证据和人工修订分层记录，不把运行时猜测当作源码事实。

依赖图提供直接／传递依赖、缺失版本、循环、冲突及受影响应用定位。需求或应用版本变化先形成影响计划：需同步的接口、任务、知识／技能等能力依据、测试矩阵、部署顺序与回退范围。计划经当前授权采用后提交唯一Go DAG，依赖分支使用独立工作树及资源预算，生成精确版本集再做独立测试。
