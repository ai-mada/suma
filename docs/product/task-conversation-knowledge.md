# 讨论中采用准确知识

T-CONTEXT-145 冻结产品范围，产品初始 1.0.0。行为以[领域合同](../../contracts/task-conversation-knowledge.md)为准；本页不作为实现、GUI 或厂商验收通过的证据。关联原 M02／M09 项目上下文与资料能力。

用户在任务讨论中明确选择已发布的项目记忆、规范或技能，让后续智能回复和开发沿用同一份可追溯依据。消息记录引用，服务端固定实际采用的正文。打开历史、发送消息、请求回复和开始开发是四个独立动作。

## 用户流程

1. 在原讨论输入区展开“添加资料”，有界搜索、翻页并选择准确发布版本；默认不添加。已选项显示标题、类型和修订。
2. 明确发送正文与引用。服务端验证当前任务写权限和全部资料资格，在原事务中保存消息、固定引用、活动及回执。
3. 从消息卡片按需展开准确历史正文。卡片保留发表时标题及修订，不跳转到后来发布的新版本。
4. 明确请求智能回复，查看所选近期消息覆盖、固定知识、模型与预算后确认。引用内容参与原来源摘要和大小限制。
5. 明确审阅真实已保存回复，再沿原开发预览与 Start 开始工作。知识继续通过原任务上下文通道传递；独立测试、正式 Review 和问题回流保持原流程。

## 发布权威与固定版本

项目知识仍由[原项目知识域](../../contracts/project-knowledge.md)管理草稿、发布、退役与批准权限；讨论不能发布、安装技能或授予工具权限。`memory`、`spec`、`skill` 均为已审阅文本，其中 skill 是工作说明。

消息输入只接受最多 16 个 `id / revision / sha256`。标题和类型由服务端从批准快照取得；调用者不能提供可信正文、标题或来源摘要。消息卡片的 `title_at_post / kind_at_post` 是历史元数据，完整正文按需读取。

| 变化 | 历史事实 | 新回复或新开发消费 |
| --- | --- | --- |
| 修改新草稿，原发布仍有效 | 原引用和发布正文保持 | 继续核验原发布，不读取新草稿 |
| 明确发布另一修订 | 原消息仍指向原修订 | 原 pin 不静默升级，需重新选择并发送新的依据 |
| 退役或正式来源版本／内容变化 | 原修订与原执行事实保留 | 当前资格核验失败，不能以历史可读绕过 |
| 当前账户失去项目权限 | 不改写原记录 | 拒绝读取／消费，界面清除受保护内容 |

准确历史接口按当前项目读取权返回指定不可变修订；它回答“当时采用了什么”，不授予“现在还能再次使用”的许可。

## 助手转述仍有依赖

近期窗口可能只有助手回答，最初附资料的人类消息已经超出窗口。助手消息仍从真实、完成的 backing Reply 继承固定知识引用，下一轮必须重新核验。它不自行声明引用，也不递归搬运整份历史来源。不能通过转述把退役或变更来源变成无来源内容。

最多取 20 条近期消息；按消息顺序汇总准确引用，同一 ID／修订／摘要去重，同一 ID 的冲突版本明确拒绝。并集最多 16 项，知识正文计入原 32,000 字节上下文和 64,000 字节最终请求限制，超限提示减少范围，不自动裁剪或生成摘要。Token、费用、模型窗口和实际用量继续分别表达。

## 恢复与边界

提交结果未知时保留原身份、项目、任务、版本、操作 ID 和原 JSON。当前权限通过后，恢复已完成的原回执先于新资料资格检查；恢复消息不再发送、不重新发布，也不自动请求模型。修改正文或 pin 是新的明确操作。

本阶段采用已有批准文本，不等于通用文件上传、二进制附件读取、Office／PDF 解析或 OCR。引用元数据、历史正文、送入模型的固定来源和真实模型用量分别记录。协议、组件或本地受控提供方证据不能称为完整厂商、安装、多机或生产验收。
