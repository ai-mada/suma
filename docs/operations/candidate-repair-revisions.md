# 修复计划修订操作与 AI SOP

状态：T-P4-033／1.0.0，2026-10-27。限定本地实际旅程、最终冷回读及主预览前向恢复／warm已验证，见[验证报告](../quality/candidate-repair-revisions-verification.md)。本页仍是受控操作规程，未执行步骤、厂商／跨机器／生产场景不因本地验证而视为完成。
依据：[033合同](../../contracts/candidate-repair-revisions.md)、[PRD](../product/candidate-repair-revisions.md)、[架构](../architecture/candidate-repair-revisions.md)、[通用运维手册](runbook.md)。

## 先确定准确对象

记录当前项目、修复任务、准备计划及原冲突计划的准确ID。若已有运行，记录run／node／attempt／fence及当前任务绑定；查看当前权限、来源验收、工具配置和执行路由。原证据与当前可执行资格分别判断。

任务运行历史中的`bound`与`observed`含义不同。观察时间不是原绑定时间；原绑定版本或时间为null时按未知展示，不用当前任务版本、日志猜测或当前时间补齐。旧链接保持准确对象，不自动切换最新计划。

## 人工操作顺序

1. 展开修复任务的“修订修复计划／Revise repair plan”，读取当前服务端上下文。仅需延长同一定义的有效期时，使用现有明确refresh。
2. 确认资格为当前待启动计划，或全部尝试已认证的执行前失败。failed标签、空输出、缺失证据和错误文字不能代替认证；未知结果先走原操作核对。
3. 选择当前合格的流程版本、agent产出节点、管理员已启用的原生工具，填写修订理由。核对固定原冲突和完整有序来源；不改任务ID、不提交替代来源，也不从浏览器修改Runner私有配置。
4. 明确确认并提交一次修订。结果应为同一任务的新计划ID、ready预览和明确父版链接；此时没有新run，也没有模型调用。失败前驱仍是任务当前运行。
5. 打开返回的准确新计划，核对新定义、路由和当前资格，再单独确认Start。版本、来源、工具或前驱恢复依据变化时，保留草稿，重新读取后再确认。
6. 观察新运行自己的产出、候选与独立正式测试。测试必须覆盖新producer封存的准确提交；原来源测试或开发自测不算本次正式测试。
7. 由有权限的人员明确Review，再按既有合同选择目标集成或绑定未开始的下游任务。记录真实运行和验收结果，保留原失败与新旧运行链接。

修订不自动启动、重试、验收或交付。每父计划只允许一个后继，版本族达到32项时保持阻断，不通过新操作编号、复制任务或改来源绕过。

## 故障判定与恢复

| 现象 | 核对事实 | 处理 |
|---|---|---|
| 待启动计划过期 | 固定任务／来源／工具／路由是否仍合格 | 同一定义使用明确refresh；重选定义使用明确修订 |
| 原工具暂停或流程不适用 | 当前资格、替代工具真实探测与授权 | 在同一任务上准备新计划，不覆盖旧计划 |
| 已知执行前失败 | 类型化证明、完整尝试集、无后继执行／候选／补偿／未知工作 | 带准确恢复SHA准备新计划，另行Start |
| 工作区准备已进入，或有模型／工作区效果 | 原运行证据、幂等定义、已执行后继 | 保留原运行，使用已有适用恢复入口；不得伪造执行前证明 |
| 结果未知或请求超时 | 原path／body／key、持久回执、准确attempt／fence | 核对原操作，不换key重发业务或自动启动替代计划 |
| 200响应结构不合法 | 原请求是否已提交、持久待核对输入 | 保留原请求，按未知结果核对；不清除后另发 |
| 409 | 当前计划头、任务／运行版本、完整来源与恢复摘要 | 保留草稿并重新读取，重新确认后才提交 |
| 401／403 | 当前实际账号与项目授权 | 隐藏受保护事实并停止写入；恢复真实权限后再读 |
| 打开被取代计划 | 父版、当前计划链接与旧运行事实 | 只读旧事实；新工作进入明确当前计划 |
| 零Token或费用未知 | 宿主证明、原结果身份、账本用量来源与价格状态 | 只有认证执行前证明可记host_startup_proof零Token；unreported／unpriced保持准确语义 |

同一原操作回执恢复不得编译或启动后继计划。被取代计划不能领取、新读代码、Start、retry或resume；准确旧结果回执和已授权cancel／reconcile保留原范围。不要删除旧尝试、重置版本、直接改任务run指针或修改数据库来制造恢复成功。

## AI执行规程

AI先读准确原冲突与当前修订上下文，只使用服务端确认的同一任务和有序来源。准备修订时说明当前阻断、新选定义及保留的旧事实；人工确认修订和Start分别发生，不能将一次确认解释为后续Review或目标写入授权。

新运行继续使用既有repair-v1和原生八工具，按宿主状态逐项解决全部来源。保持受限工作区、当前文件CAS、固定检查和最终封存，不丢弃后续来源，不以原测试或前缀提交冒充完整候选。碰到未知状态，停止产生新副作用并核对原操作。

AI报告要区分“已创建新预览”“已启动新运行”“已封存候选”“独立测试已通过”“已明确验收”和“已完成下游交付”。只有实际收到并核对相应证据，才报告该状态。用户理由、路径、代码与原证明保留原文，系统说明随当前中英语言显示。

## 维护与证据

验证复用未变来源和032的Git／SDK证据，只对变化的权限、并发、CAS、历史、回执及私有／Pool接缝执行必要检查。实际旅程需分别证明待启动修订、真实宿主执行前失败、健康工具的新运行、准确候选独立测试与Review；不以夹具或定向检查代替厂商、物理多机或生产事实。

维护前盘点并保留唯一来源、数据库、截图和交付证据。临时产物放仓库忽略缓存，保持进程本地TEMP／TMP；不得在盘根散建目录。现有主预览、凭据和用户浏览器在完成明确前向升级前保持原状。提交只含必要源码、合同、文档和精简证据，不含缓存、数据库、Token、原始日志或二进制。完整P0–P7继续实施。
