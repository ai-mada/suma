# Persistent DAG engine

当前增量实现、准入与迁移规范见 [持久化增量调度内核](incremental-kernel.md)。以下接口与节点说明同步适用；T-P4-005 的代际、窗口和测试范围以该专项文档及正式验收记录为准。

`internal/dag` is an executable SQL-backed state machine. Workflows contain a real directed acyclic graph: explicit `edges` and each node's `depends_on` are combined and deduplicated; a conditional explicit edge takes precedence over a duplicate dependency. Publication rejects cycles, missing endpoints, duplicate IDs, invalid joins and unsafe automatic retries. Published versions are immutable. A run pins the latest published version at creation and continues to use that snapshot after subsequent publications.

## State and transaction boundary

Nodes move from `pending` to `ready`, `waiting`, or `skipped`; a claimed node becomes `running` with a distinct attempt and monotonically increasing node fence. Successful/failed/stopped results finish an attempt. An expired lease or a reported unknown external outcome becomes `reconciling`. Such work retains its reservations and is never automatically replayed. An authorized reconciliation needs `node_id`, `outcome` (`not_started`, `succeeded`, `failed`) and a nonempty evidence `reason`.

Mutations lock the project and root-run family, sample database time, validate current state, settle the affected persistent dependency frontier, and save dirty records. Events receive globally ordered cursors only at the final transaction tail, after domain writes and hooks; no other locks or domain queries follow that append. Read APIs do not acquire mutation locks. The platform retains current organization authorization locking, so this is not a claim of complete organization sharding or cross-tenant fairness. No external command or model call occurs in a transaction.

`CreateRun` and `Command` require an operation ID. A reused key with a different request is a conflict. Exact duplicates return the existing run. `PublishWithOperation` atomically commits the published version and receipt, including when the server generates the workflow ID. `CreateRunVersion` pins an explicit published version (zero selects latest). `CreateRunBound` additionally invokes a service binding callback in the same SQL transaction before readiness is visible; its digest includes the binding identity, and duplicate receipt replay does not repeat the callback. A failing binding rolls back the run, nodes, events, readiness and receipt. The callback must use its provided SQL transaction exclusively and perform no external calls. Commands also require the current run version, with duplicate operations recognized before version checking. Results carry their own operation ID, attempt, fence and worker identity. Duplicates have no second effect; mismatched or late attempts are rejected. No claim promises exactly-once external side effects: effectful tasks must implement idempotency at their destination.

Leases default to 30 database seconds. `Heartbeat` extends only the current unexpired assignment. `Tick` durably marks expired assignments as unknown and releases elapsed timers. The service must call `Tick` periodically. Wall clocks on runners do not determine lease ownership.

## Joins and conditions

| Join | Readiness | Unsatisfiable path |
| --- | --- | --- |
| `all_success` (generation 2 default) | All incoming edges resolve and every selected required parent succeeds | Skip if all are unselected or a selected required parent fails |
| `all_done` | All parents terminate and at least one incoming edge is active | Skip when every incoming edge is inactive |
| `any_success` | The first successful active parent, even while other parents are running | Skip once all parents terminate without an active success |
| `quorum` | `quorum` successful active parents, potentially before other parents terminate | Skip once the threshold cannot be reached |

A join is enqueued once. Sibling failures remain recorded; any failed node makes the final run `failed`, including when an `all_done` cleanup or an `any_success` continuation succeeds. Cancellation takes precedence over final failure.

Node `condition` is a bounded predicate: `true`, `false`, `ancestor.state == succeeded` or `ancestor.output == value`. Optional single/double quotes around the right-hand value are accepted. References must be declared graph ancestors. A predicate waits for the referenced ancestor to terminate, including when an early any-success/quorum join is otherwise ready. This does not execute JavaScript, shell, or arbitrary expressions. A false predicate skips its node and propagates through downstream joins.

Edge conditions support `success`/`succeeded`, `failure`/`failed`, `skipped`, `cancelled`, `always`/`all_done`, or an exact match against the parent output. Omitted conditions are active. A `condition` node runs inside the engine and emits `true`/`false` from `config.expression`. Alternatively `branches` maps branch labels to predicates: the first matching label in sorted order is emitted; a predicate `default` supplies a fallback label. Branch edge conditions match that label. Use `all_done` for convergence over skipped branches.

## Node kinds and durable waits

`task`, `command`, `script`, `test` and `agent` are dispatched to a worker. `external_workflow` is dispatched only to a worker advertising its configured plugin protocol. `join` and `noop` complete internally. An `approval` node waits durably with no worker claim. The `approval` or `approve` command accepts approved/rejected decisions and uses the run version to reject stale decisions. A `timer` waits until its database timestamp, using nonnegative `config.duration_seconds`; it consumes no worker slot.

A `map` node expands `config.items` into at most 1,000 durable child records named `map_id[index]`. `config.template` may override the task template; otherwise children inherit the map command, retry/idempotency flags, timeout and resource requests. `{{item}}` and `{{index}}` are substituted within individual command arguments. The engine does not invoke a shell. Each child receives `config.item` and `config.index`. The parent waits without a lease and succeeds only after all children succeed. The full immutable manifest and digests persist first; children materialize in atomic chunks of at most 128 with a CAS boundary. The parent cannot finish before expansion closes. Restart resumes the committed boundary without duplicating children. Nested map templates are explicitly unsupported. Retry an individual failed idempotent child; the engine reopens its map parent and skipped descendants. Retrying the map parent itself is unsupported to avoid replaying successful children.

Generation 2 automatic retry requires `idempotent` and explicit `failure_class=transient`, permits at most two additional attempts, and persists 1/2-second backoff and a total execution window (configured timeout or 300 seconds). Explicit manual retry starts a new window generation and preserves the old one. Unknown outcomes require reconciliation first. Explicit retry also requires a failed idempotent node and refuses to replay already executed descendants. Runs can pause admission while existing workers finish. Resume recomputes readiness. Cancel marks unclaimed nodes cancelled and requests stops from current workers; the run remains `cancelling` while any claimed or unknown work remains. A matching `stopped` result or an evidence-bearing reconciliation resolves that work. `ErrCancelled` from heartbeat is a stop request, never proof that a process exited.

## Versioned subworkflows

A `subworkflow` node requires `config.workflow_id` and a positive integer `config.workflow_version`. Publication resolves that exact immutable version in the same tenant and project; missing, cross-project, or unpinned references fail. Nested references are bounded to 32 levels and the materialized graph, including map fanout into subworkflows, is bounded to 10,000 nodes. This is a validation limit, not a throughput result.

The engine creates a child run inside the same transaction and binds `(parent_run_id, node_id, attempt)` to exactly one child run. The parent node becomes `waiting` and does not consume a worker lease. `child_run_id` is available on its public node state. The child has independent attempts, events, immutable workflow version and failure evidence. Its terminal result updates the waiting parent and downstream readiness in the same transaction. Engine restart does not create a second child. A failed idempotent subworkflow can retry with a new attempt and child run; previous failed children remain readable. Generation 2 does not infer that a failed child workflow is transient, so it does not automatically replay that child; an authorized explicit retry creates a new child and retains all previous evidence.

Pause propagates to running child runs. Resume affects only children that this parent paused; an independently paused child remains paused. A child cannot bypass a paused/cancelled/finished parent by independently resuming or reopening execution. Cancellation propagates recursively and leaves the parent waiting while any descendant worker or unknown external outcome still needs stop evidence. An optional subworkflow `timeout_seconds` is an absolute database deadline from child creation, including paused time: expiry requests recursive child cancellation and marks the parent node failed only after the child has stopped. Children hold their own resource reservations. Subworkflow input/output mapping is not a general expression engine: the invocation pins the published child definition, and its parent output records child run identity/state for inspection.

## External workflow protocol

`external_workflow` requires `config.plugin`, `config.workflow` and optional object `config.input`. Its command must be empty. The engine passes this configuration in the assignment and requires an exact `external_workflow:<plugin>` capability. Generic command or external capabilities cannot claim it. An unavailable plugin leaves the node ready; it cannot become successful through configuration alone. Assignment-provided endpoint overrides are rejected.

The runner owns its administrator-configured provider endpoint and credentials, durable dispatch journal, remote creation/poll/cancel protocol and actual terminal evidence. Dispatch uses the assignment's run/node/attempt/fence identity. A remote cancellation acknowledgement alone does not establish stop. Lost or unknown results follow the same reconciling/fencing rules as other external effects. Local fake-provider protocol tests are distinct from verification against a real deployed provider.

## Explicit compensation runs

A successful worker node may declare `config.compensation` as an explicit unconditional worker-node template (`type`, command/config, timeout, resources, idempotency and retry settings). The engine does not infer inverse operations. An authorized `compensate` command requires a terminal source run, its current version, an operation key and a nonempty reason. Optional `node_ids` selects configured successful nodes; omitting it selects all successful configured worker nodes in that run. A request with no eligible definitions fails.

In one transaction, the engine verifies the original successful attempts and fences, publishes a separate immutable compensation workflow, creates its run, and records fixed source references. Ordering reverses the original dependency reachability, including intervening nodes without compensation and expanded map children. Parallel original effects retain parallel inverses. An inverse failure blocks earlier dependent inverses, while retaining both original and compensation evidence. Compensation does not automatically traverse child-run effects across a subworkflow boundary.

Each inverse assignment receives `config.source_execution` with source run/node/attempt/fence/worker and SHA-256 of source output. The immutable attempt result remains the full evidence source. Templates may bind `{{source.run_id}}`, `{{source.node_id}}`, `{{source.attempt}}`, `{{source.fence}}` and `{{source.output}}` inside individual command arguments or configuration strings. Replacement is one pass, with no shell evaluation. External inverse inputs also receive `source_execution`. Generated definitions over 2 MiB fail atomically.

The source run keeps its historical state and exposes `compensation_run_id` and `compensation_state`. Compensation state changes append source events and advance its version. Generated inverse workflows are internal evidence: public workflow lists hide them, while `GetWorkflow` can inspect the pinned graph. Their entire workflow identity is blocked from public dispatch, republishing or subworkflow reuse, so a fresh operation key cannot replay the same generated inverse graph. The source cannot be retried after compensation starts; create a new run with a new execution basis. A compensation run cannot itself be compensated. Acceptance gates must reject source evidence with a compensation link, including compensated child runs.

`CommandWithHook` allows the service to revoke existing task acceptance atomically with a compensation command. Its callback runs after the validated transition and before receipt commit, using only the supplied SQL transaction. Callback failure rolls back the entire command; receipt replay does not invoke it again. This avoids a window in which compensation is admitted while the associated task still exposes accepted evidence. A compensation run reporting success proves only that the explicitly configured inverse graph completed; it does not prove a universal rollback, atomic undo of remote systems, or restoration of every business invariant.

## Admission and fairness

Ready work is persistent. Claiming chooses the least recently served eligible run within the authenticated project and then the oldest ready node. The durable claim sequence rotates across runs. Ineligible capabilities or insufficient resources do not block later candidates. `config.capability` optionally requires a matching worker capability.

`Engine.SetResourceLimits` configures per-project integer capacities; node `resources` requests are reserved atomically with the claim. Ordinary resource reservations remain held through unknown outcomes and release only after terminal results, actual stop proof or reconciliation. A stopped process with unknown external effect remains `reconciling`; only process-class resources release, while effect-class resources remain held until reconciliation. The reserved resource name `budget` is a cumulative per-attempt admission budget and is not refunded. Resources without configured limits have unlimited admission; configuring actual capacities is an administrative responsibility. This is a project capacity ledger, not measured runner hardware inventory, financial billing, or a cost estimator.

## Verification and limits

The SQLite test suite exercises diamonds with parallel branches, cycle rejection, concurrent claims from separate engine connections, result duplication and fencing, tenant isolation, immutable versions, restart recovery, approval version conflicts, conditional branch skips, early any-success/quorum joins, all-done cleanup preserving failure, retry fences, timers, pause/resume, cancellation stop evidence, resource retention on unknown outcomes, budgets, run rotation, map expansion/restart, versioned subworkflow lifecycle/deadlines/retry, plugin capability admission, reverse compensation dependencies, original attempt references, compensation failure and map compensation after restart. The T-P4-005 SQLite evidence additionally measures a 1,000-node/2,994-edge graph and hot paths with driver-level SQL/read/write counts; it does not establish distributed production throughput.

OceanBase MySQL mode and PostgreSQL drivers and dialect handling are present; no external database instance was available for integration verification. Generic `external`/HTTP nodes and a generic `compensation` node type are rejected; remote workflows use `external_workflow`, while compensation is an explicit generated run. No arbitrary code sandbox, distributed worker discovery, nested map template expansion, general subworkflow parameter mapping, automatic cross-subworkflow rollback, or real-provider reconciliation adapter is implemented by this package. The HTTP service and runner own authentication, authorization, process execution, and external evidence collection.
